> [!DANGER] শুধু নিজের প্রজেক্ট, নিজের রিপো, অনুমতি নিয়ে
> এই লেসনের সব খোঁজাখুঁজি শুধু নিজের অ্যাপ, নিজের GitHub রিপো, নিজের Stripe Sandbox বা অফিসের যে সিস্টেম টেস্ট করার লিখিত অনুমতি আছে সেখানে। অন্যের সাইট বা অন্যের পাবলিক রিপোতে key খুঁজে বেড়ানো, পাওয়া key দিয়ে "শুধু দেখার জন্য" একটা কল করাও অপরাধ হতে পারে। কিছু পেলে ব্যবহার করবেন না, শুধু দায়িত্বশীলভাবে জানান: [নৈতিকতা ও দায়িত্বশীল প্রকাশ](/lessons/ethics-responsible-disclosure/)।

Sensitive Data Exposure (সংবেদনশীল তথ্য অনিচ্ছাকৃতভাবে বাইরে চলে যাওয়া) পেমেন্ট সিস্টেমে সবচেয়ে বেশি পাওয়া যায় এমন বাগগুলোর একটা। এখানে আক্রমণকারীকে কিছু ভাঙতে হয় না। দরজা খোলা থাকে, শুধু ঢুকে পড়লেই হলো।

একটা Secret Key ফাঁস মানে আপনার দোকানের ক্যাশবাক্সের চাবি রাস্তায় পড়ে থাকা। এই লেসনে শিখব কোথায় কোথায় চাবি পড়ে থাকে, আর টেস্টার হিসেবে কীভাবে খুঁজে বের করবেন।

## এই লেসনে যা শিখবেন

- Stripe-এর key-গুলোর পার্থক্য: কোনটা পাবলিক, কোনটা গোপন
- ফ্রন্টএন্ড বান্ডলে secret key খোঁজা (DevTools Sources)
- GitHub, লগ, স্ক্রিনশট ও টিকেটে key ফাঁস, আর gitleaks / trufflehog দিয়ে নিজের রিপো স্ক্যান
- API রেসপন্সে অতিরিক্ত ডেটা: DevTools Network ট্যাব ধাপে ধাপে
- Error message-এ stack trace, SQL, ভার্সন ফাঁস
- PAN ও CVC কেন কখনো লগ বা সংরক্ষণ করা যাবে না, মাস্কিং (last4)
- ফাঁস হওয়া key পেলে কী করবেন

## কোন key কোথায় থাকতে পারে

| Key | উদাহরণ | কোথায় থাকতে পারে | ফাঁস হলে ঝুঁকি |
|---|---|---|---|
| Publishable key | `pk_test_XXXXXXXX` | ব্রাউজার, মোবাইল অ্যাপ | কম; এটা পাবলিক হওয়ার জন্যই বানানো |
| Secret key | `sk_test_XXXXXXXXXXXXXXXX` | শুধু সার্ভারের এনভায়রনমেন্ট ভেরিয়েবল বা সিক্রেট ম্যানেজার | সর্বোচ্চ; রিফান্ড, কাস্টমার ডেটা পড়া, সব কিছু |
| Restricted key | `rk_test_XXXX` | সার্ভার, নির্দিষ্ট কাজে সীমিত অনুমতি | অনুমতির উপর নির্ভর করে |
| Webhook secret | `whsec_XXXXXXXX` | শুধু সার্ভার | নকল webhook গ্রহণযোগ্য হয়ে যায় |

লাইভ key-এর শুরুতে `sk_live_` বা `rk_live_` থাকে। টেস্ট key দিয়ে আসল টাকা যায় না, কিন্তু স্যান্ডবক্সের সব ডেটা পড়া ও বদলানো যায়। তাই টেস্ট key ফাঁসও রিপোর্ট করার মতো বাগ, আর সেটা দেখায় যে একই পথে লাইভ key-ও ফাঁস হতে পারে। বিস্তারিত: [docs.stripe.com/keys](https://docs.stripe.com/keys)।

## ফ্রন্টএন্ড বান্ডলে Secret Key খোঁজা

নতুন ডেভেলপাররা প্রায়ই `.env` ফাইলে `VITE_STRIPE_SECRET` বা `NEXT_PUBLIC_STRIPE_SECRET` রাখেন। এই prefix-ওয়ালা ভেরিয়েবল বিল্ডের সময় সরাসরি JS ফাইলে ঢুকে যায়, আর সবাই ডাউনলোড করতে পারে।

ধাপে ধাপে (নিজের অ্যাপে):

1. Chrome-এ নিজের অ্যাপের চেকআউট পেজ খুলুন।
2. `F12` চেপে DevTools খুলুন, **Sources** ট্যাবে যান।
3. `Ctrl+Shift+F` (Mac-এ `Cmd+Option+F`) চাপুন। সব লোড হওয়া ফাইলে সার্চের প্যানেল খুলবে।
4. একে একে সার্চ করুন: `sk_live_`, `sk_test_`, `rk_live_`, `rk_test_`, `whsec_`।
5. আরও সার্চ করুন: `secret`, `apiKey`, `password`, `Authorization`।

স্ক্রিনশট বর্ণনা: নিচের দিকে Search প্যানেলে ফাইলের নাম (যেমন `assets/index-a1b2c3.js`) এবং তার নিচে মিলে যাওয়া লাইন হলুদ হাইলাইটে দেখা যাচ্ছে। লাইনে ক্লিক করলে উপরে সেই ফাইলের ঠিক জায়গাটা খুলে যায়।

> [!TIP] Minified ফাইল পড়া
> বিল্ড করা JS এক লাইনে চাপা থাকে। Sources-এ ফাইলের নিচে `{}` (Pretty print) বোতাম চাপলে সুন্দর করে সাজানো দেখাবে।

`pk_test_` পাওয়া স্বাভাবিক। `sk_` বা `whsec_` পাওয়া মানে **High থেকে Critical** বাগ, লাইভ হলে Critical।

## GitHub, লগ, স্ক্রিনশট ও টিকেট

### GitHub

একবার কোনো key commit হলে, পরের commit-এ মুছে দিলেও Git history-তে থেকে যায়। পাবলিক রিপো হলে বট কয়েক মিনিটের মধ্যে খুঁজে পায়।

GitHub-এর দুটো ফিচার জানুন:

- **Secret scanning**: রিপোতে পরিচিত ফরম্যাটের key খুঁজে সতর্ক করে। Stripe-সহ অনেক সার্ভিস GitHub-এর পার্টনার, পাবলিক রিপোতে তাদের key পাওয়া গেলে সার্ভিসকেও জানানো হয়।
- **Push protection**: push করার সময়ই key ধরা পড়লে push আটকে দেয়।

রিপোর Settings → Code security (বা Security) অংশে এগুলো চালু আছে কি না দেখুন। বিস্তারিত GitHub Docs-এ "secret scanning" লিখে সার্চ করুন: [docs.github.com](https://docs.github.com)।

### gitleaks ও trufflehog দিয়ে নিজের রিপো স্ক্যান

এ দুটো ফ্রি ওপেন সোর্স টুল। **শুধু নিজের বা অনুমতি পাওয়া রিপোতে চালান।**

```bash
# gitleaks: পুরো git history স্ক্যান (নিজের রিপোর ফোল্ডারে)
gitleaks detect --source . -v

# trufflehog: লোকাল git রিপো স্ক্যান
trufflehog git file://. --only-verified
```

`--only-verified` শুধু সেই key দেখায় যা টুল যাচাই করে সক্রিয় পেয়েছে। খেয়াল করুন, যাচাই মানে টুল ওই সার্ভিসে একটা কল করে। তাই এটাও শুধু নিজের রিপোতেই চালাবেন। ইনস্টলের নিয়ম প্রতিটি টুলের GitHub পেজে আছে (GitHub-এ "gitleaks" ও "trufflehog" সার্চ করুন)।

### লগ

ডিবাগের সময় ডেভেলপার লেখেন `console.log(req.headers)` বা `logger.info(stripeConfig)`। এতে `Authorization: Bearer sk_test_...` সরাসরি লগে চলে যায়। লগ অনেক মানুষ পড়ে: সাপোর্ট, DevOps, তৃতীয় পক্ষের লগ সার্ভিস।

টেস্টার হিসেবে নিজের স্টেজিংয়ে একটা পেমেন্ট করে লগ ফাইল বা লগ ড্যাশবোর্ডে সার্চ করুন: `sk_`, `whsec_`, `Bearer`, `card`, `cvc`, `4242`।

### স্ক্রিনশট ও টিকেট

বাগ রিপোর্টে Postman-এর স্ক্রিনশট দিলেন, Authorization ট্যাবে key পরিষ্কার দেখা যাচ্ছে। Jira বা Trello-তে সেটা আজীবন থেকে যায়। তাই স্ক্রিনশট দেওয়ার আগে key ঝাপসা করুন, Postman-এ key সবসময় Environment-এর `secret` টাইপ ভেরিয়েবলে রাখুন।

## API রেসপন্সে অতিরিক্ত ডেটা: DevTools Network ধাপে ধাপে

Excessive Data Exposure (API প্রয়োজনের চেয়ে বেশি তথ্য পাঠায়, আর UI শুধু দরকারিটুকু দেখায়) OWASP API Security Top 10-এর পরিচিত সমস্যা। মানুষ ভাবে "স্ক্রিনে তো দেখা যায় না", কিন্তু Network ট্যাবে সবই দেখা যায়।

1. নিজের অ্যাপে লগইন করুন, DevTools → **Network** ট্যাব খুলুন।
2. উপরের ফিল্টারে **Fetch/XHR** বাছুন, যাতে শুধু API কল দেখা যায়।
3. **Preserve log** টিক দিন, যাতে পেজ বদলালেও লিস্ট না মোছে।
4. প্রোফাইল, অর্ডার হিস্টরি, চেকআউট পেজ ঘুরে আসুন।
5. প্রতিটি রিকোয়েস্টে ক্লিক করে **Response** বা **Preview** ট্যাব দেখুন।
6. UI-তে যা দেখায় আর রেসপন্সে যা আছে, পাশাপাশি তুলনা করুন।

স্ক্রিনশট বর্ণনা: বাম দিকে রিকোয়েস্টের তালিকা (`me`, `orders`, `cart`), ডান দিকে Preview ট্যাবে JSON গাছের মতো খোলা। `user` অবজেক্টের ভেতরে `password_hash` ও `is_admin` লাইন দেখা যাচ্ছে।

খারাপ রেসপন্সের উদাহরণ:

```json
{
  "id": 1042,
  "name": "Rahim Uddin",
  "email": "r***@example.com",
  "password_hash": "$2b$10$XXXXXXXXXXXXXXXX",
  "is_admin": false,
  "internal_notes": "VIP, refund manually",
  "stripe_customer_id": "cus_XXXXXXXX",
  "card": { "brand": "visa", "last4": "4242", "exp_month": 12, "exp_year": 2030 }
}
```

এখানে কী কী সমস্যা:

- `password_hash` কখনো ক্লায়েন্টে যাবে না
- `internal_notes` ও `is_admin` অভ্যন্তরীণ তথ্য
- `stripe_customer_id` নিজে গোপন না হলেও দরকার না থাকলে পাঠানোর কারণ নেই
- `last4` দেখানো ঠিক আছে, এটা মাস্ক করা তথ্য

> [!NOTE]
> অন্য ইউজারের id বসিয়ে (যেমন `/api/users/1043`) তার ডেটা আসে কি না, সেটা আলাদা দুর্বলতা: IDOR। সেটা আমরা [অথেন্টিকেশন ও অথরাইজেশন টেস্টিং](/lessons/auth-authorization-testing/) লেসনে দেখেছি।

## Error Message-এ তথ্য ফাঁস

ভুল ইনপুট দিলে অ্যাপ কী বলে? ভালো অ্যাপ বলে "কিছু একটা ভুল হয়েছে, রেফারেন্স: ERR-8F2A"। খারাপ অ্যাপ বলে:

```text
SequelizeDatabaseError: column "coupon_cod" does not exist
    at Query.formatError (/var/www/shop/node_modules/sequelize/lib/dialects/postgres/query.js:...)
SELECT * FROM coupons WHERE coupon_cod = 'TEST'
X-Powered-By: Express
Server: nginx/1.18.0
```

এখানে ফাঁস হলো: ডাটাবেসের ধরন, টেবিল ও কলামের নাম, সার্ভারের ফোল্ডার পাথ, ফ্রেমওয়ার্ক ও ওয়েব সার্ভারের ভার্সন। আক্রমণকারী এখন জানে কোন পুরনো ভার্সনের দুর্বলতা খুঁজতে হবে।

যাচাই করতে নিজের অ্যাপে চেষ্টা করুন:

- খালি বা অনেক লম্বা ইনপুট, ভুল টাইপ (সংখ্যার জায়গায় লেখা)
- ভুল JSON বডি পাঠানো (যেমন শেষের `}` বাদ দিয়ে)
- নেই এমন রুট: `/api/orders/abc`
- রেসপন্স হেডারে `X-Powered-By`, `Server` ভার্সন দেখুন

## PAN ও CVC: কখনো লগ বা সংরক্ষণ নয়

PAN (Primary Account Number, কার্ডের ১৬ ডিজিটের নম্বর) ও CVC (কার্ডের পেছনের ৩–৪ ডিজিট) সবচেয়ে সংবেদনশীল তথ্য।

| তথ্য | সংরক্ষণ করা যাবে? | দেখানোর নিয়ম |
|---|---|---|
| পুরো PAN | মার্চেন্টের নিজের সিস্টেমে না রাখাই নিয়ম; রাখলে কঠোর এনক্রিপশন ও PCI দায়িত্ব | কখনো পুরোটা নয় |
| last4 | হ্যাঁ | `•••• 4242` |
| মেয়াদ (expiry) | সাধারণত হ্যাঁ | `12/30` |
| CVC/CVV | **কখনো না**, অনুমোদনের পরে একদমই না | কখনো না |
| কার্ডধারীর নাম | হ্যাঁ, সতর্কতার সাথে | প্রয়োজনমতো |

Stripe Elements বা Checkout ব্যবহার করলে কার্ডের নম্বর আপনার সার্ভারে আসেই না, Stripe একটা টোকেন বা PaymentMethod id (`pm_...`) দেয়। তাই আপনার লগে বা ডাটাবেসে কোথাও ১৬ ডিজিটের কার্ড নম্বর পাওয়া গেলে, সেটা মানে কোথাও নিয়ম ভাঙা হয়েছে। বিস্তারিত: [PCI DSS বেসিক](/lessons/pci-dss-basics/)।

টেস্ট আইডিয়া: স্টেজিংয়ে `4242 4242 4242 4242` দিয়ে পেমেন্ট করে লগ, ডাটাবেস, ইমেইল রসিদ ও অ্যাডমিন প্যানেলে `4242424242424242` সার্চ করুন। শুধু last4 পাওয়া উচিত।

## ফাঁস হওয়া key পেলে কী করবেন

1. **ব্যবহার করবেন না।** "আসল কি না" দেখতে একটা কলও না।
2. **গোপনে জানান।** নিজের টিম হলে টিম লিড বা সিকিউরিটি দলকে সরাসরি মেসেজে; বাইরের প্রতিষ্ঠান হলে তাদের security contact বা `security.txt`-এ দেওয়া ঠিকানায়।
3. **কোথায় পেয়েছেন, কখন, কীভাবে** লিখুন; key-এর শুধু প্রথম কয়েক অক্ষর দিন, পুরোটা নয়।
4. **Rotate করানো।** Stripe Dashboard → Developers → API keys-এ key "roll" করে নতুন key বানানো যায়, পুরনোটা বাতিল হয়। এটা মালিকের কাজ।
5. **অপব্যবহার যাচাই।** Dashboard-এর লগে অচেনা কল আছে কি না মালিক দেখবেন।
6. **মূল কারণ ঠিক করা।** History থেকে মোছা, push protection চালু, এনভায়রনমেন্ট ভেরিয়েবলে সরানো।

> [!MISTAKE] সাধারণ ভুল
> - "এটা তো test key" বলে রিপোর্ট না করা।
> - Commit মুছে দিয়ে ভাবা সমস্যা শেষ; key rotate না করা।
> - বাগ রিপোর্টে পুরো key পেস্ট করা।
> - শুধু UI দেখে টেস্ট শেষ করা, Network ট্যাবের রেসপন্স না দেখা।
> - অন্যের পাবলিক রিপোতে gitleaks বা trufflehog চালানো।

## হাতেকলমে অনুশীলন

1. নিজের একটা ছোট প্রজেক্টে (বা [Playwright লেসনের](/lessons/playwright-api-ui-testing/) ডেমো অ্যাপে) ইচ্ছে করে `.env`-এ `VITE_STRIPE_SECRET=sk_test_XXXXXXXXXXXXXXXX` রেখে বিল্ড করুন।
2. DevTools Sources-এ `sk_test_` সার্চ করে খুঁজে বের করুন।
3. নতুন একটা নিজের প্রাইভেট GitHub রিপো বানিয়ে ওই ফাইল commit করুন, তারপর মুছে আরেকটা commit দিন।
4. `gitleaks detect --source . -v` চালিয়ে দেখুন পুরনো commit থেকেও ধরা পড়ে কি না।
5. OWASP Juice Shop লোকালে চালিয়ে Network ট্যাবে বিভিন্ন API রেসপন্স দেখুন, কোন রেসপন্সে অপ্রয়োজনীয় ফিল্ড আছে লিখুন।
6. প্রতিটি ফাইন্ডিং নিয়ে একটা ছোট বাগ রিপোর্ট লিখুন, key-এর পুরো মান না দিয়ে।

> [!CHECK] সফলতার চেকলিস্ট
> - আপনি জানেন কোন key পাবলিক আর কোনটা নয়
> - Sources ও Network দুই ট্যাবেই খুঁজতে পারেন
> - নিজের রিপো স্ক্যান করে history থেকেও key বের করতে পেরেছেন
> - ফাঁস পেলে কী করবেন, ৬ ধাপ মুখস্থ

## সারসংক্ষেপ

- `pk_` পাবলিক; `sk_`, `rk_`, `whsec_` শুধু সার্ভারে। টেস্ট key ফাঁসও রিপোর্টযোগ্য।
- Key ফাঁসের জায়গা: ফ্রন্টএন্ড বান্ডল, Git history, লগ, স্ক্রিনশট, টিকেট।
- UI যা দেখায় না, Network ট্যাবে তা দেখা যায়; API থেকেই অতিরিক্ত ফিল্ড বাদ দিতে হবে।
- Error-এ stack trace, SQL, ভার্সন নয়; সাধারণ বার্তা ও রেফারেন্স id।
- PAN কখনো পুরোটা দেখানো নয়, CVC কখনো সংরক্ষণ নয়; শুধু last4।
- ফাঁস পেলে: ব্যবহার নয়, গোপনে জানানো, rotate।
