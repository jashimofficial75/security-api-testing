ফাংশনালি ঠিক চলা চেকআউট পেজও ভিড়ের সময় ভেঙে পড়তে পারে। ১১.১১ সেল বা ঈদের অফারে Daraz-এর মতো শপে একসাথে হাজার মানুষ "Pay Now" চাপলে কী হয়, সেটা আগে থেকে জানার উপায় হলো **লোড টেস্টিং**।

এই লেসনে আমরা ফ্রি ও ওপেন সোর্স টুল **k6** দিয়ে নিজের চেকআউট ব্যাকএন্ডে নিরাপদভাবে লোড টেস্ট করা শিখব।

## এই লেসনে যা শিখবেন

- Performance testing ও load testing কী, আর পেমেন্ট সিস্টেমে কেন জরুরি
- k6 ইনস্টল করা এবং প্রথম স্ক্রিপ্ট (`http.get`, `check`, `sleep`) লেখা
- VU, duration, stages (ধীরে বাড়ানো ও কমানো) বোঝা
- thresholds দিয়ে পাস/ফেল শর্ত লেখা (`p(95)<500`, `rate<0.01`)
- k6-এর summary output পড়া
- ৫ ধরনের লোড টেস্ট: smoke, load, stress, spike, soak
- কেন কখনো Stripe বা অন্য কারো API-তে লোড টেস্ট করবেন না

## পারফরম্যান্স টেস্টিং কী এবং কেন

**Performance testing** (সিস্টেম কত দ্রুত ও কতটা স্থিরভাবে কাজ করে তা মাপা) হলো একটা বড় ছাতা। এর ভেতরে **Load testing** (প্রত্যাশিত পরিমাণ ইউজার দিয়ে সিস্টেম চালিয়ে দেখা) সবচেয়ে বেশি ব্যবহৃত।

একটা সহজ উপমা দিই। ঢাকার একটা রেস্টুরেন্ট সাধারণ দিনে ৫০ জনকে ভালো সার্ভ করে। কিন্তু ইফতারের সময় ২০০ জন এলে রান্নাঘর, ক্যাশ কাউন্টার, ওয়েটার সবাই চাপে পড়ে। কোথায় আগে আটকায়, সেটা জানাই লোড টেস্টের কাজ।

পেমেন্ট সিস্টেমে ধীরগতির ফল খুব খারাপ:

- ইউজার "Pay" চেপে অপেক্ষা করতে করতে আবার চাপে, ফলে **ডাবল অর্ডার** বা ডাবল চার্জের ঝুঁকি (Idempotency লেসনটা মনে করুন: [/lessons/idempotency-testing/](/lessons/idempotency-testing/))
- টাইমআউট হলে অর্ডার "pending" অবস্থায় আটকে থাকে
- Webhook প্রসেসিং পিছিয়ে যায়, ইউজার টাকা দিয়েও কনফার্মেশন পায় না
- ডাটাবেস কানেকশন শেষ হয়ে গেলে পুরো সাইট ডাউন

### কয়েকটা জরুরি শব্দ

| শব্দ | সহজ মানে |
|---|---|
| Latency / Response time | একটা রিকোয়েস্টের উত্তর আসতে কত সময় লাগল |
| Throughput | প্রতি সেকেন্ডে কতগুলো রিকোয়েস্ট সার্ভ হলো (RPS) |
| Error rate | মোট রিকোয়েস্টের কত শতাংশ ফেল করল |
| Percentile (p95) | ৯৫% রিকোয়েস্ট এই সময়ের মধ্যে শেষ হয়েছে; বাকি ৫% এর চেয়ে ধীর |
| VU (Virtual User) | k6-এর একজন কাল্পনিক ইউজার, যে স্ক্রিপ্টটা বারবার চালায় |

## নিরাপত্তা আগে: কোথায় লোড টেস্ট করবেন

> [!LIVE] Stripe বা অন্যের API-তে কখনো লোড টেস্ট নয়
> Stripe-এর API-তে rate limit আছে, Test Mode-এও (sandbox-এ সীমা সাধারণত Live-এর চেয়েও কম)। সীমা পার হলে `429 Too Many Requests` আসবে, আর ইচ্ছা করে Stripe-কে চাপ দিলে আপনার অ্যাকাউন্ট সীমিত বা বন্ধ হতে পারে। বিস্তারিত: [Stripe rate limits](https://docs.stripe.com/rate-limits)।
>
> সঠিক পদ্ধতি: **নিজের চেকআউট ব্যাকএন্ড, নিজের staging বা লোকাল এনভায়রনমেন্টে** টেস্ট করুন, আর ভেতরের Stripe কলগুলো **mock বা stub** (নকল সার্ভিস যা আসল Stripe-এর মতো উত্তর দেয়) দিয়ে বদলে দিন। একই নিয়ম bKash, SSLCommerz বা যেকোনো তৃতীয় পক্ষের ক্ষেত্রেও।

অনুশীলনের জন্য k6 নিজেই ডেমো টার্গেট দেয়:

- **quickpizza.grafana.com**: Grafana-র বানানো ডেমো অ্যাপ, k6-এর নতুন ডকুমেন্টেশনের উদাহরণগুলো এটা ব্যবহার করে
- **test-api.k6.io**: পুরোনো উদাহরণে দেখা যায়; এটা চালু না থাকলে QuickPizza ব্যবহার করুন

তবে ডেমো সাইটেও ছোট লোড দিন (কয়েকটা VU, অল্প সময়)। এগুলো শেখার জন্য, শত শত VU চালানোর জন্য নয়।

> [!DANGER] অনুমতি ছাড়া কারো সাইটে লোড টেস্ট মানে আক্রমণ
> অন্যের সার্ভারে লিখিত অনুমতি ছাড়া বড় লোড পাঠানো DoS (Denial of Service) আক্রমণের মতো দেখায় এবং আইনি সমস্যা তৈরি করতে পারে। নিজের অফিসের প্রোডাকশনেও টিম লিড ও DevOps-এর অনুমতি ছাড়া চালাবেন না।

## k6 ইনস্টল ও প্রথম স্ক্রিপ্ট

k6 একটা কমান্ড লাইন টুল। স্ক্রিপ্ট লেখা হয় JavaScript-এ, কিন্তু চলে k6-এর নিজস্ব ইঞ্জিনে (Node.js লাগে না)। অফিসিয়াল ডকুমেন্টেশন: [k6 docs](https://grafana.com/docs/k6/latest/) এবং হোমপেজ [k6.io](https://k6.io)।

### ইনস্টল

```bash
# macOS
brew install k6

# Windows (দুটোর যেকোনো একটা)
winget install k6 --source winget
choco install k6

# Docker (যেকোনো OS)
docker run --rm -i grafana/k6 run - < first-test.js

# ইনস্টল ঠিক হয়েছে কিনা
k6 version
```

Linux (Ubuntu/Debian)-এর জন্য k6 ডকুমেন্টেশনের "Install k6" পেজে apt রিপোজিটরি যোগ করার কমান্ড আছে, সেখান থেকে কপি করুন।

### প্রথম স্ক্রিপ্ট

`first-test.js` নামে একটা ফাইল বানান:

```js
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  vus: 5,          // একসাথে ৫ জন ভার্চুয়াল ইউজার
  duration: '30s', // ৩০ সেকেন্ড ধরে চলবে
};

export default function () {
  const res = http.get('https://quickpizza.grafana.com/');

  check(res, {
    'status is 200': (r) => r.status === 200,
    'body is not empty': (r) => r.body && r.body.length > 0,
  });

  sleep(1); // আসল ইউজারের মতো ১ সেকেন্ড বিরতি
}
```

চালান:

```bash
k6 run first-test.js
```

এখানে কী হচ্ছে, লাইন ধরে বুঝি:

- `http.get()` একটা GET রিকোয়েস্ট পাঠায় এবং response ফেরত দেয়
- `check()` হলো assertion-এর মতো, কিন্তু ফেল করলেও টেস্ট থামে না; শুধু গুনে রাখে কত শতাংশ পাস করল
- `sleep(1)` "think time" (ইউজার পেজ পড়ছে, ফর্ম পূরণ করছে) অনুকরণ করে; না দিলে VU-রা অবাস্তব গতিতে রিকোয়েস্ট পাঠায়
- `default function` প্রতিটা VU বারবার চালায়; প্রতিবার চালানোকে বলে একটা **iteration**

> [!TIP] CLI থেকে দ্রুত বদলান
> স্ক্রিপ্ট না বদলে `k6 run --vus 2 --duration 10s first-test.js` দিয়েও VU ও সময় বদলানো যায়। URL এনভায়রনমেন্ট ভেরিয়েবলে রাখুন: `k6 run -e BASE_URL=http://localhost:3000 test.js`, আর স্ক্রিপ্টে `__ENV.BASE_URL` পড়ুন। এতে একই স্ক্রিপ্ট লোকাল ও staging দুই জায়গায় চলে।

## Stages ও Thresholds: বাস্তব লোড আর পাস/ফেল শর্ত

বাস্তবে ইউজার একসাথে লাফিয়ে আসে না, ধীরে ধীরে বাড়ে। **stages** দিয়ে ramp up (ধীরে বাড়ানো) আর ramp down (ধীরে কমানো) লেখা যায়।

**thresholds** হলো টেস্টের পাস/ফেল নিয়ম। যেমন "৯৫% রিকোয়েস্ট ৫০০ms-এর কম হতে হবে" আর "ফেল রেট ১%-এর কম"। থ্রেশহোল্ড ভাঙলে k6 শেষে ফেল দেখায় এবং non-zero exit code দেয়, তাই CI-তে বসালে জব লাল হয়ে যায় ([/lessons/cicd-github-actions/](/lessons/cicd-github-actions/) দেখুন)।

নিচের স্ক্রিপ্ট নিজের লোকাল চেকআউট API (যেখানে Stripe কল mock করা) টেস্ট করে:

```js
import http from 'k6/http';
import { check, sleep } from 'k6';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:3000';

export const options = {
  stages: [
    { duration: '1m', target: 20 },  // ১ মিনিটে ০ থেকে ২০ VU
    { duration: '3m', target: 20 },  // ৩ মিনিট ২০ VU-তে স্থির
    { duration: '1m', target: 0 },   // ১ মিনিটে নামিয়ে ০
  ],
  thresholds: {
    http_req_duration: ['p(95)<500'], // ৯৫% রিকোয়েস্ট ৫০০ms-এর কম
    http_req_failed: ['rate<0.01'],   // ফেল ১%-এর কম
    checks: ['rate>0.99'],            // ৯৯%-এর বেশি check পাস
  },
};

export default function () {
  const payload = JSON.stringify({
    items: [{ sku: 'TSHIRT-01', qty: 1 }],
    currency: 'bdt',
  });

  const res = http.post(`${BASE_URL}/api/checkout`, payload, {
    headers: {
      'Content-Type': 'application/json',
      'Idempotency-Key': `load-${__VU}-${__ITER}`, // প্রতি iteration-এ আলাদা
    },
  });

  check(res, {
    'status is 200': (r) => r.status === 200,
    'has order id': (r) => r.json('orderId') !== undefined,
  });

  sleep(Math.random() * 2 + 1); // ১–৩ সেকেন্ড বিরতি
}
```

খেয়াল করুন:

- `__VU` (VU নম্বর) আর `__ITER` (iteration নম্বর) দিয়ে প্রতিটা রিকোয়েস্টের জন্য আলাদা Idempotency-Key বানানো হয়েছে। সব রিকোয়েস্টে একই key দিলে সার্ভার প্রথমটার ফলই বারবার ফেরত দেবে, আর আপনি আসল লোড মাপতেই পারবেন না।
- এখানে কোনো API key নেই। লোকাল ব্যাকএন্ড নিজের `.env` থেকে key পড়ে, আর লোড টেস্টের সময় সেটা mock Stripe-এ কল করে।

### Stripe কল mock করার একটা সহজ ধারণা

ব্যাকএন্ডে একটা সুইচ রাখুন, যেমন `PAYMENTS_MODE=mock`। এই মোডে "PaymentIntent তৈরি" ফাংশনটা আসল Stripe-এ না গিয়ে ৫০–১৫০ms অপেক্ষা করে একটা নকল উত্তর দেয়:

```js
// ব্যাকএন্ডের ভেতরে (ধারণা দেখানোর জন্য)
async function createPaymentIntent(amount, currency) {
  if (process.env.PAYMENTS_MODE === 'mock') {
    await new Promise((r) => setTimeout(r, 50 + Math.random() * 100));
    return { id: `pi_mock_${Date.now()}`, status: 'requires_payment_method', amount, currency };
  }
  return stripe.paymentIntents.create({ amount, currency });
}
```

এভাবে আপনি নিজের কোড, ডাটাবেস, কিউ আর সার্ভারের সক্ষমতা মাপছেন, Stripe-এর নয়। Contract testing লেসনে Prism দিয়ে OpenAPI থেকে mock সার্ভার বানানোও দেখব ([/lessons/contract-testing-openapi/](/lessons/contract-testing-openapi/))।

## k6-এর summary output পড়া

টেস্ট শেষে k6 টার্মিনালে একটা সারাংশ দেখায়। ভার্সন ভেদে সাজানো একটু আলাদা হতে পারে, তবে মূল মেট্রিকগুলো এমন:

```text
  █ THRESHOLDS
    http_req_duration
    ✓ 'p(95)<500' p(95)=312.45ms
    http_req_failed
    ✗ 'rate<0.01' rate=2.10%

  █ TOTAL RESULTS
    checks_succeeded...: 97.90%  4895 out of 5000
    checks_failed......: 2.10%   105 out of 5000
    http_req_duration..: avg=148ms min=42ms med=120ms max=2.1s p(90)=260ms p(95)=312ms
    http_req_failed....: 2.10%   105 out of 5000
    http_reqs..........: 5000    16.6/s
    iterations.........: 5000    16.6/s
    vus................: 1       min=1  max=20
    vus_max............: 20
```

কীভাবে পড়বেন:

| মেট্রিক | কী দেখবেন |
|---|---|
| `http_req_duration` | avg-এর চেয়ে p(95) ও max বেশি গুরুত্বপূর্ণ; ধীর লেজটা (tail) এখানে ধরা পড়ে |
| `http_req_failed` | 4xx/5xx বা নেটওয়ার্ক এরর কত শতাংশ |
| `http_reqs` | মোট রিকোয়েস্ট ও প্রতি সেকেন্ডে কত (throughput) |
| `checks` | আপনার লেখা check কত শতাংশ পাস |
| `iterations` | VU-রা মোট কতবার default function চালিয়েছে |
| `vus`, `vus_max` | কতজন ভার্চুয়াল ইউজার সক্রিয় ছিল |

উপরের উদাহরণে latency ঠিক আছে, কিন্তু ফেল রেট ২.১%। তাই থ্রেশহোল্ড ফেল। পরের ধাপ: সার্ভারের লগে দেখুন কোন রিকোয়েস্ট কেন ফেল করেছে (৫০০? ডাটাবেস টাইমআউট? ৪২৯?)। এই তদন্তের কৌশল observability লেসনে আছে ([/lessons/observability-incidents/](/lessons/observability-incidents/))।

> [!NOTE] গড় কেন ধোঁকা দেয়
> ধরুন ৯৫ জন ১০০ms-এ উত্তর পেল আর ৫ জন ৪ সেকেন্ডে। গড় দাঁড়ায় প্রায় ২৯৫ms, যা "ভালো" মনে হয়। কিন্তু ওই ৫ জন হয়তো অধৈর্য হয়ে আবার "Pay" চেপেছে। তাই থ্রেশহোল্ড সবসময় percentile (p95, p99) দিয়ে লিখুন।

## ৫ ধরনের লোড টেস্ট

একই স্ক্রিপ্ট, শুধু stages বদলে ভিন্ন প্রশ্নের উত্তর পাওয়া যায়:

| টাইপ | প্রশ্ন | লোডের আকার (উদাহরণ) | কখন চালাবেন |
|---|---|---|---|
| Smoke | স্ক্রিপ্ট ও সিস্টেম মোটামুটি কাজ করছে তো? | ১–২ VU, ১ মিনিট | প্রতিটা নতুন স্ক্রিপ্টের পর, প্রতি PR-এ |
| Load | স্বাভাবিক ভিড়ে লক্ষ্য পূরণ হয়? | প্রত্যাশিত গড় ইউজার, ১০–৩০ মিনিট | রিলিজের আগে |
| Stress | সীমার বাইরে গেলে কী হয়, কোথায় ভাঙে? | ধাপে ধাপে স্বাভাবিকের ২–৩ গুণ বা আরও | সক্ষমতা পরিকল্পনায় |
| Spike | হঠাৎ বিশাল ভিড় সামলাতে পারে? | কয়েক সেকেন্ডে অনেক VU, তারপর দ্রুত নামা | ফ্ল্যাশ সেল, ঈদ অফারের আগে |
| Soak | লম্বা সময় চললে ধীর হয়ে যায় কি? | মাঝারি লোড, কয়েক ঘণ্টা | মেমরি লিক, কানেকশন লিক খুঁজতে |

একটা spike টেস্টের stages দেখতে এমন:

```js
export const options = {
  stages: [
    { duration: '30s', target: 5 },    // স্বাভাবিক
    { duration: '10s', target: 200 },  // হঠাৎ ভিড় (রাত ১২টার অফার)
    { duration: '1m', target: 200 },   // ভিড় চলছে
    { duration: '10s', target: 5 },    // দ্রুত নেমে আসা
    { duration: '1m', target: 5 },     // সিস্টেম কি স্বাভাবিকে ফিরল?
  ],
};
```

Spike-এর পর শেষ ধাপটা খুব জরুরি। ভিড় চলে যাওয়ার পরও যদি error rate বেশি থাকে, তার মানে সিস্টেম নিজে থেকে সেরে উঠতে পারছে না।

### পেমেন্ট QA হিসেবে লোড টেস্টে কী খুঁজবেন

- ভিড়ের সময় **ডুপ্লিকেট অর্ডার** তৈরি হচ্ছে কি? (টেস্ট শেষে DB-তে orderId গুনে মিলিয়ে দেখুন)
- স্টক ১০টা থাকলে ১১টা বিক্রি হয়ে যাচ্ছে কি? (race condition)
- Webhook কিউ কত পিছিয়ে যাচ্ছে, সব ইভেন্ট শেষে প্রসেস হলো কি?
- টাইমআউট হলে ইউজার পরিষ্কার মেসেজ পাচ্ছে, নাকি সাদা পেজ?
- লোড শেষে "pending" অবস্থায় আটকে থাকা অর্ডার কতগুলো?

## হাতেকলমে অনুশীলন

1. k6 ইনস্টল করুন এবং `k6 version` চালিয়ে নিশ্চিত হন।
2. উপরের `first-test.js` কপি করে `--vus 1 --duration 10s` দিয়ে একটা smoke test চালান। সব check সবুজ কিনা দেখুন।
3. স্ক্রিপ্টে একটা check ইচ্ছা করে ভুল লিখুন (যেমন `r.status === 201`)। আবার চালান এবং `checks` মেট্রিকে কী বদলায় দেখুন। লক্ষ্য করুন, check ফেল করলেও টেস্ট থামেনি।
4. options-এ `thresholds: { checks: ['rate>0.99'] }` যোগ করুন। এখন একই ভুল check থাকলে k6 শেষে ফেল দেখাবে। টার্মিনালে `echo $?` (Windows PowerShell-এ `$LASTEXITCODE`) চালিয়ে exit code দেখুন।
5. stages দিয়ে ছোট একটা ramp লিখুন: ২০ সেকেন্ডে ০→৫ VU, ৩০ সেকেন্ড ৫ VU, ১০ সেকেন্ডে ৫→০। QuickPizza-তে চালান (ছোট লোড রাখুন)।
6. নিজের কোনো লোকাল প্রজেক্ট থাকলে (যেমন capstone-এর চেকআউট API, [/capstone/](/capstone/)), Stripe কল mock করে সেখানে `-e BASE_URL=http://localhost:3000` দিয়ে load test চালান।
7. summary থেকে p(95), http_req_failed আর http_reqs একটা ছোট টেস্ট রিপোর্টে লিখুন: কত VU, কত সময়, ফলাফল, থ্রেশহোল্ড পাস/ফেল।

> [!CHECK] সফলতার চেকলিস্ট
> - smoke test-এ সব check পাস হচ্ছে
> - থ্রেশহোল্ড ভাঙলে k6 non-zero exit code দিচ্ছে, সেটা নিজের চোখে দেখেছেন
> - stages দিয়ে ramp up/down লিখতে পারছেন
> - রিপোর্টে avg নয়, p95 দিয়ে কথা বলছেন

> [!MISTAKE] সাধারণ ভুল
> - Stripe, bKash বা অন্য কারো API-তে সরাসরি লোড পাঠানো। Test Mode-ও rate limited, অ্যাকাউন্ট সীমিত হতে পারে।
> - `sleep()` না দেওয়া, ফলে ৫ VU-ই অবাস্তবভাবে হাজার রিকোয়েস্ট পাঠায়।
> - নিজের ল্যাপটপের সীমা ভুলে যাওয়া: ধীর Wi-Fi বা দুর্বল CPU থেকে বড় টেস্ট চালালে ফলাফল মাপে আপনার মেশিন, সার্ভার নয়।
> - শুধু গড় দেখে "পারফরম্যান্স ভালো" বলা।
> - সব রিকোয়েস্টে একই Idempotency-Key বা একই টেস্ট ডেটা ব্যবহার করা, ফলে ক্যাশ থেকে উত্তর আসে।
> - স্ক্রিপ্টে আসল API key বা পাসওয়ার্ড লিখে রিপোজিটরিতে commit করা।

## সারসংক্ষেপ

- লোড টেস্ট দেখায় ভিড়ের সময় চেকআউট কোথায় ধীর হয় বা ভাঙে; পেমেন্টে এর ফল ডাবল অর্ডার ও আটকে থাকা পেমেন্ট।
- k6 স্ক্রিপ্ট: `http.get/post` দিয়ে রিকোয়েস্ট, `check` দিয়ে যাচাই, `sleep` দিয়ে বাস্তব বিরতি।
- `vus`/`duration` সহজ লোড, `stages` দিয়ে ramp up/down; `thresholds` দিয়ে পাস/ফেল ও CI-বান্ধব exit code।
- রিপোর্টে p95, error rate আর throughput দেখুন, শুধু গড় নয়।
- smoke, load, stress, spike, soak: একই স্ক্রিপ্ট, ভিন্ন প্রশ্ন।
- লোড টেস্ট শুধু নিজের সিস্টেমে, Stripe কল mock করে; অনুশীলনে k6-এর ডেমো টার্গেট, তাও ছোট লোডে।

## বাড়ির কাজ

1. QuickPizza-র বিরুদ্ধে একটা smoke test আর একটা ছোট load test (সর্বোচ্চ ১০ VU) লিখুন, দুটোতেই thresholds রাখুন।
2. নিজের ভাষায় একটা ছোট নোট লিখুন: Daraz-এর মতো শপের "ঈদ মেগা সেল"-এর আগে কোন ৩টা টেস্ট টাইপ চালাবেন এবং কেন।
