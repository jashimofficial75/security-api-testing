## GitHub রিপো: আপনার কাজের শোকেস

একটা ভালো রিপো দশটা সার্টিফিকেটের চেয়ে বেশি কথা বলে। ইন্টারভিউয়ার ২–৩ মিনিট দেখবেন, তাই সাজানো আর পরিষ্কার হওয়া জরুরি।

### README-তে যা থাকবে

1. **এক লাইনে প্রজেক্ট**: "Stripe Sandbox-এ একটা কোর্স-বিক্রির চেকআউট ফ্লোর API, webhook ও UI টেস্টিং।"
2. **ব্যাজ**: GitHub Actions-এর স্ট্যাটাস ব্যাজ, যাতে দেখা যায় টেস্ট সবুজ। ব্যাজের Markdown আপনার workflow-এর Actions পেজ থেকে "Create status badge" অপশনে পাবেন ([/lessons/cicd-github-actions/](/lessons/cicd-github-actions/))।
3. **কী টেস্ট করা হয়েছে**: একটা ছোট টেবিল (API: ৪৫টা, webhook: ১২টা, UI: ৮টা, security চেক: ১০টা)।
4. **কীভাবে চালাবেন**: `npm ci`, `.env.example` কপি করে `.env`, `npx newman run ...`, `npx playwright test`।
5. **উল্লেখযোগ্য বাগ**: ২–৩টা বাগ রিপোর্টের লিংক, এক লাইনের বর্ণনাসহ।
6. **টুল**: Postman, Newman, Playwright, Stripe CLI, k6, GitHub Actions।
7. **বাংলা সারাংশ**: বাংলাদেশি নিয়োগকর্তাদের জন্য ৪–৫ লাইন।
8. **নিরাপত্তা নোট**: "সব টেস্ট শুধু Stripe Test Mode-এ; কোনো আসল key বা কার্ড ডেটা নেই।"

> [!DANGER] পাবলিক রিপোতে secret নয়, কখনো নয়
> Commit করার আগে `git diff` দেখুন। `.env` অবশ্যই `.gitignore`-এ। Postman environment এক্সপোর্টের আগে সব key-র মান মুছুন। ভুল করে একটা key commit হলে শুধু ফাইল মুছলে হবে না, git history-তে থেকে যায়: সঙ্গে সঙ্গে Stripe Dashboard থেকে key রোল (বাতিল ও নতুন) করুন ([/lessons/sensitive-data-exposure/](/lessons/sensitive-data-exposure/))। আর আগের অফিস বা ক্লায়েন্টের কোনো তথ্য, স্ক্রিনশট বা বাগ রিপোর্ট অনুমতি ছাড়া পোর্টফোলিওতে নয়।

Test Mode-এ আসল টাকা নড়ে না, টেস্ট কার্ড ও `sk_test_` key ব্যবহার হয়, ডেটা Live থেকে আলাদা। QA সব টেস্ট Test Mode/Sandbox-এ করে; Live-এ শুধু অনুমোদিত, নিয়ন্ত্রিত smoke চেক হতে পারে, দায়িত্বপ্রাপ্তদের অনুমতিতে।

</details>

**২. একটা চেকআউটের জন্য আপনি কোন কোন টেস্ট কেস লিখবেন?**

<details><summary>সমাধান দেখুন</summary>

সফল পেমেন্ট; decline (insufficient funds, expired card, incorrect CVC); 3D Secure প্রয়োজন এমন কার্ড; ডাবল ক্লিক; নেটওয়ার্ক টাইমআউট; ইউজার মাঝপথে ট্যাব বন্ধ; amount বদলানোর চেষ্টা; কারেন্সি; রিফান্ড ও আংশিক রিফান্ড; webhook দেরিতে বা দুবার আসা; মোবাইল ভিউ। প্রতিটায় UI, DB আর Stripe তিন জায়গায় ফল মেলাতে হয়।

</details>

**৩. Stripe-এ amount 125000 মানে কী?**

<details><summary>সমাধান দেখুন</summary>

Stripe amount নেয় smallest currency unit-এ। BDT-তে ১২৫০০০ পয়সা = ১২৫০ টাকা, USD-তে ১২৫০০০ সেন্ট = ১২৫০ ডলার। কিছু zero-decimal কারেন্সিতে (যেমন JPY) এই নিয়ম আলাদা, তাই কারেন্সি অনুযায়ী টেস্ট দরকার।

</details>

**৪. পেমেন্ট সফল হয়েছে কিনা অ্যাপ কীভাবে জানবে: redirect দেখে নাকি webhook দেখে?**

<details><summary>সমাধান দেখুন</summary>

চূড়ান্ত সত্যের উৎস সার্ভার-সাইড: webhook (signature যাচাইসহ) বা সার্ভার থেকে API দিয়ে PaymentIntent-এর স্ট্যাটাস আনা। ব্রাউজার redirect শুধু ইউজারকে পেজ দেখানোর জন্য, কারণ ইউজার সেটা বানাতে বা বাদ দিতে পারে। SSLCommerz-এও একই: Validation API ছাড়া paid নয়।

</details>

**৫. Idempotency কী, পেমেন্টে কেন জরুরি?**

<details><summary>সমাধান দেখুন</summary>

একই রিকোয়েস্ট বারবার পাঠালেও ফল একবারই হবে। নেটওয়ার্ক টাইমআউটে ক্লায়েন্ট retry করলে যেন দুবার চার্জ না হয়। Stripe-এ `Idempotency-Key` হেডার দিয়ে; টেস্টে একই key দিয়ে দুবার POST করে দেখি একই অবজেক্ট ফেরত আসে, আর একই key-তে ভিন্ন বডি দিলে এরর আসে।

</details>

**৬. রিকনসিলিয়েশনে কোন ধরনের অমিল খোঁজেন?**

<details><summary>সমাধান দেখুন</summary>

Missing in DB, missing in Stripe, amount mismatch, status mismatch, duplicate। মেলানো হয় PaymentIntent id বা metadata order_id দিয়ে, amount একই ইউনিটে, একই টাইমজোনের cut-off-এ। শুধু মোট অংক নয়, লাইন-বাই-লাইন।

</details>

### API টেস্টিং

**৭. ৪০১ আর ৪০৩-এর পার্থক্য কী?**

<details><summary>সমাধান দেখুন</summary>

401 Unauthorized: পরিচয় দেওয়া হয়নি বা ভুল (key/token নেই বা অবৈধ)। 403 Forbidden: পরিচয় ঠিক, কিন্তু এই কাজের অনুমতি নেই। যেমন অন্য ইউজারের অর্ডার দেখতে চাইলে 403 বা 404 প্রত্যাশিত।

</details>

**৮. একটা API রেসপন্সে আপনি কী কী যাচাই করেন?**

<details><summary>সমাধান দেখুন</summary>

Status code, রেসপন্স টাইম, হেডার (Content-Type), বডির স্কিমা (ফিল্ড, type, required), মান সঠিক কিনা (amount, currency, status), এরর মেসেজ অর্থবহ কিনা আর তাতে সংবেদনশীল তথ্য ফাঁস হচ্ছে কিনা। পরে DB বা অন্য endpoint দিয়ে side effect যাচাই।

</details>

**৯. Postman collection আর environment কেন আলাদা রাখেন? Newman কী করে?**

<details><summary>সমাধান দেখুন</summary>

Collection-এ রিকোয়েস্ট ও টেস্ট, environment-এ base URL ও key-র মতো পরিবর্তনশীল মান। এতে একই collection লোকাল, staging-এ চলে আর key রিপোতে যায় না। Newman হলো Postman collection কমান্ড লাইনে চালানোর টুল, তাই CI-তে চালানো ও HTML রিপোর্ট বানানো যায়।

</details>

**১০. Pagination কীভাবে টেস্ট করবেন?**

<details><summary>সমাধান দেখুন</summary>

প্রথম পেজ, শেষ পেজ, `limit`-এর সীমা (০, ১, সর্বোচ্চ, সর্বোচ্চের বেশি), পরের পেজের cursor (Stripe-এ `starting_after` ও `has_more`), পেজের মধ্যে ডুপ্লিকেট বা বাদ পড়া আইটেম, আর খালি তালিকা।

</details>

**১১. Contract testing কেন দরকার?**

<details><summary>সমাধান দেখুন</summary>

API-র আকার (ফিল্ড, type) অজান্তে বদলে গেলে (schema drift) মোবাইল/ওয়েব ক্লায়েন্ট ভাঙে, কিন্তু status 200-ই থাকে। OpenAPI স্পেক বা JSON Schema দিয়ে রেসপন্সের আকার যাচাই করলে এমন breaking change মার্জের আগে ধরা পড়ে।

</details>

### Webhook টেস্টিং

**১২. Webhook আর polling-এর পার্থক্য কী?**

<details><summary>সমাধান দেখুন</summary>

Polling-এ আপনার অ্যাপ বারবার জিজ্ঞেস করে "কিছু হলো?"। Webhook-এ ঘটনা ঘটলে Stripe নিজেই আপনার URL-এ HTTP POST পাঠায়। Webhook দ্রুত ও কার্যকর, কিন্তু নিরাপত্তা (signature), ডুপ্লিকেট আর ক্রম ঠিক না থাকা সামলাতে হয়।

</details>

**১৩. Webhook signature verification কীভাবে টেস্ট করবেন?**

<details><summary>সমাধান দেখুন</summary>

সঠিক secret-এ ইভেন্ট: 2xx। ভুল secret, signature হেডার বাদ, বডির একটা অক্ষর বদলানো, পুরোনো timestamp (replay): প্রতিটায় 400 এবং কোনো অর্ডার পরিবর্তন নয়। Raw body দিয়ে যাচাই হচ্ছে কিনা (পার্স করা JSON নয়) সেটাও দেখি।

</details>

**১৪. Webhook একই ইভেন্ট দুবার পাঠালে কী হবে?**

<details><summary>সমাধান দেখুন</summary>

Stripe at-least-once ডেলিভারি করে, তাই ডুপ্লিকেট স্বাভাবিক। হ্যান্ডলার event id সেভ করে আগে প্রসেস হয়েছে কিনা দেখবে। টেস্ট: Stripe CLI বা Dashboard থেকে একই ইভেন্ট resend, তারপর অর্ডার, ইমেইল, স্টক একবারই বদলেছে কিনা যাচাই।

</details>

**১৫. লোকালে webhook টেস্ট করবেন কীভাবে?**

<details><summary>সমাধান দেখুন</summary>

`stripe listen --forward-to localhost:3000/webhook` দিয়ে Stripe CLI ইভেন্ট লোকালে ফরোয়ার্ড করে, আর `stripe trigger payment_intent.succeeded` দিয়ে ইভেন্ট তৈরি করা যায়। CLI যে `whsec_` secret দেখায় সেটা লোকাল env-এ দিতে হয়। অন্য গেটওয়ের জন্য ngrok-এর মতো টানেল বা webhook.site দিয়ে বডি দেখা যায়।

</details>

**১৬. Webhook ইভেন্ট ভুল ক্রমে এলে কী সমস্যা হতে পারে?**

<details><summary>সমাধান দেখুন</summary>

যেমন `charge.refunded` আগে, `payment_intent.succeeded` পরে এলে অ্যাপ রিফান্ড হওয়া অর্ডারকে আবার paid করে দিতে পারে। হ্যান্ডলারকে স্ট্যাটাস পিছিয়ে না নেওয়ার নিয়ম মানতে হয় বা সন্দেহ হলে API থেকে সর্বশেষ অবস্থা আনতে হয়। টেস্টে ইচ্ছা করে ক্রম উল্টে পাঠাই।

</details>

### Security টেস্টিং

**১৭. পেমেন্টে কোন লজিক বাগ খুঁজবেন?**

<details><summary>সমাধান দেখুন</summary>

ক্লায়েন্ট থেকে পাঠানো দাম বা amount বদলানো, ঋণাত্মক পরিমাণ, কুপন একাধিকবার, অন্য ইউজারের অর্ডার id দিয়ে অ্যাক্সেস (IDOR), পেমেন্ট ছাড়া success পেজে গিয়ে অর্ডার পাওয়া, race condition-এ স্টকের বেশি বিক্রি। সবই শুধু নিজের sandbox অ্যাপ বা অনুমোদিত ল্যাবে।

</details>

**১৮. Card testing আক্রমণ কী, কীভাবে শনাক্ত ও প্রতিরোধ হয়?**

<details><summary>সমাধান দেখুন</summary>

চুরি হওয়া কার্ড নম্বর বৈধ কিনা দেখতে আক্রমণকারী ছোট ছোট অনেক পেমেন্ট চেষ্টা করে। লক্ষণ: decline rate হঠাৎ বাড়া, একই IP/ডিভাইস থেকে অনেক চেষ্টা। প্রতিরোধ: rate limiting, CAPTCHA, Stripe Radar-এর মতো fraud নিয়ম, অ্যালার্ট। QA হিসেবে ধারণা ও প্রতিরক্ষা যাচাই করি, আক্রমণ অটোমেট করি না।

</details>

**১৯. PCI DSS কী, QA হিসেবে কেন জানা দরকার?**

<details><summary>সমাধান দেখুন</summary>

কার্ড ডেটা সুরক্ষার আন্তর্জাতিক মানদণ্ড। Stripe Elements/Checkout ব্যবহার করলে কার্ড ডেটা মার্চেন্টের সার্ভারে আসে না, তাই দায় অনেক কমে। QA যাচাই করে কার্ড নম্বর আমাদের সার্ভারে, লগে বা DB-তে যাচ্ছে না, আর পেমেন্ট পেজ HTTPS-এ।

</details>

**২০. টেস্ট করতে গিয়ে কোনো সাইটে সিকিউরিটি বাগ পেলে কী করবেন?**

<details><summary>সমাধান দেখুন</summary>

নিজের কোম্পানির সিস্টেম হলে অভ্যন্তরীণ প্রক্রিয়ায় গোপনে রিপোর্ট। বাইরের সাইট হলে আর পরীক্ষা নয়, ডেটা অ্যাক্সেস বা শেয়ার নয়; তাদের responsible disclosure বা bug bounty নীতি (যেমন security.txt) মেনে রিপোর্ট। অনুমতি ছাড়া কারো সাইটে security টেস্টিং করি না।

</details>

আরও দ্রুত রিভিশনের জন্য [/cheatsheet/](/cheatsheet/) পেজটা হাতের কাছে রাখুন।

6. Commit-এর আগে টার্মিনালে `git grep -n "sk_test_"` চালান; শুধু `XXXX` প্লেসহোল্ডার আসা উচিত।
