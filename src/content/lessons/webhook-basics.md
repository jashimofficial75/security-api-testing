এ পর্যন্ত আমরা নিজেরাই Stripe-কে প্রশ্ন করেছি: "এই পেমেন্টের অবস্থা কী?" কিন্তু বাস্তব অ্যাপে উল্টোটাও দরকার: কিছু ঘটলে **Stripe নিজেই** আপনার সার্ভারকে জানাবে।

এই ব্যবস্থার নাম **Webhook** (কোনো ঘটনা ঘটলে এক সিস্টেম অন্য সিস্টেমের URL-এ নিজে থেকে HTTP POST পাঠায়)। পেমেন্ট QA-র অর্ধেক বাগ লুকিয়ে থাকে এখানেই।

## এই লেসনে যা শিখবেন

- Webhook কী, একটা সহজ দেশি উদাহরণে
- Polling আর Webhook-এর পার্থক্য
- পেমেন্ট ফ্লোতে Webhook-এর ভূমিকা, আর কেন success পেজ পেমেন্টের প্রমাণ নয়
- Stripe Event অবজেক্টের গঠন
- গুরুত্বপূর্ণ ইভেন্টগুলো আর প্রতিটায় অ্যাপের কী করা উচিত
- এন্ডপয়েন্টের জন্য মূল নিয়ম: দ্রুত 2xx

## Webhook: কুরিয়ারের ফোন

ধরুন আপনি অনলাইনে একটা বই অর্ডার করেছেন। দুইভাবে জানতে পারেন বই কখন আসবে।

**উপায় ১ (Polling):** প্রতি ঘণ্টায় কুরিয়ার অফিসে ফোন করে জিজ্ঞেস করা, "আমার পার্সেল কি এসেছে?" বেশিরভাগ উত্তর "না, এখনো না।" আপনার সময় আর ফোনের বিল দুটোই নষ্ট।

**উপায় ২ (Webhook):** কুরিয়ারকে আপনার নম্বর দিয়ে রাখা। পার্সেল পৌঁছালে **ডেলিভারিম্যান নিজেই ফোন** করবেন: "ভাই, আপনার পার্সেল নিচে।"

Webhook হলো দ্বিতীয় উপায়। আপনার সার্ভার একটা URL (যেমন `https://shop.example.com/webhooks/stripe`) Stripe-কে দিয়ে রাখে। পেমেন্ট সফল হলে, ব্যর্থ হলে বা রিফান্ড হলে Stripe ঐ URL-এ একটা POST রিকোয়েস্ট পাঠায়, বডিতে থাকে ঘটনার বিস্তারিত।

### Polling বনাম Webhook

| বিষয় | Polling | Webhook |
|---|---|---|
| কে যোগাযোগ শুরু করে | আপনার সার্ভার, বারবার | Stripe, ঘটনা ঘটলে |
| তথ্য কত দ্রুত | পরের প্রশ্নের সময় পর্যন্ত দেরি | প্রায় সাথে সাথে |
| রিকোয়েস্টের অপচয় | অনেক (বেশিরভাগ "কোনো পরিবর্তন নেই") | শুধু দরকারে |
| রেট লিমিটের ঝুঁকি | বেশি | কম |
| সার্ভারকে পাবলিক URL লাগে? | না | হ্যাঁ (ইন্টারনেট থেকে পৌঁছানো যায় এমন) |
| জটিলতা | সহজ | সিগনেচার যাচাই, retry, ডুপ্লিকেট সামলাতে হয় |
| পেমেন্টে ব্যবহার | মাঝে মাঝে ব্যাকআপ হিসেবে (reconciliation) | মূল ভরসা |

> [!NOTE]
> বাংলাদেশের গেটওয়েগুলোতেও একই ধারণা আছে। যেমন SSLCommerz-এ IPN (Instant Payment Notification) নামে পেমেন্টের পর সার্ভারে নোটিফিকেশন পাঠানোর ব্যবস্থা আছে। নাম ভিন্ন, ধারণা একই। বিস্তারিত [বাংলাদেশি গেটওয়ে Sandbox](/lessons/bangladesh-gateways-sandbox/) লেসনে।

## পেমেন্ট ফ্লোতে Webhook-এর ভূমিকা

একটা কোর্স-বিক্রির সাইটে Stripe Checkout দিয়ে পেমেন্টের ধাপগুলো দেখি:

1. গ্রাহক "কিনুন" চাপেন। সার্ভার Checkout Session বানিয়ে গ্রাহককে Stripe-এর পেজে পাঠায়।
2. গ্রাহক কার্ড দিয়ে পে করেন।
3. Stripe গ্রাহকের ব্রাউজারকে `success_url`-এ রিডাইরেক্ট করে।
4. **আলাদাভাবে**, Stripe সার্ভারের Webhook URL-এ `checkout.session.completed` ইভেন্ট পাঠায়।
5. সার্ভার ইভেন্ট যাচাই করে অর্ডার "Paid" করে, কোর্সে অ্যাক্সেস দেয়, রসিদ ইমেইল করে।

ধাপ ৩ আর ৪ আলাদা রাস্তা। একটা যায় ব্রাউজার দিয়ে, অন্যটা সরাসরি সার্ভারে।

### কেন success পেজ পেমেন্টের প্রমাণ নয়

> [!DANGER] success পেজে অর্ডার Paid করা একটা নিরাপত্তা বাগ
> যদি অ্যাপ শুধু `/success` পেজ লোড হলেই অর্ডার "Paid" করে, তাহলে যে কেউ পেমেন্ট না করেই ব্রাউজারে ঐ URL টাইপ করে কোর্স পেয়ে যেতে পারে। নিজের টেস্ট অ্যাপে এটা যাচাই করুন, অন্যের সাইটে কখনো নয়। এ ধরনের লজিক বাগ নিয়ে বিস্তারিত [পেমেন্ট লজিক দুর্বলতা](/lessons/payment-logic-vulnerabilities/) লেসনে।

success পেজের আরও সমস্যা:

- গ্রাহক পে করার পর ইন্টারনেট চলে গেলে বা ট্যাব বন্ধ করলে রিডাইরেক্ট কখনো হয় না। টাকা কাটল, কিন্তু অর্ডার "Pending" থেকে গেল।
- কিছু পেমেন্ট মেথডে (যেমন ব্যাংক ডেবিট) টাকা নিশ্চিত হতে ঘণ্টা বা দিন লাগে। রিডাইরেক্টের সময় পেমেন্ট এখনো চূড়ান্ত নয়।
- success পেজ শুধু UX: "ধন্যবাদ, আমরা আপনার পেমেন্ট প্রসেস করছি।"

**নিয়ম:** success পেজ দেখায়, Webhook (অথবা সার্ভার থেকে Stripe API কল করে যাচাই) সিদ্ধান্ত নেয়।

## Stripe Event অবজেক্টের গঠন

Stripe যা পাঠায় তা একটা **Event** অবজেক্ট। একটা নমুনা (কিছু ফিল্ড বাদ দিয়ে সংক্ষেপে):

```json
{
  "id": "evt_TEST1a2b3c4d",
  "object": "event",
  "api_version": "2024-06-20",
  "created": 1793600000,
  "livemode": false,
  "pending_webhooks": 1,
  "request": {
    "id": "req_TESTabc123",
    "idempotency_key": "order-DRZ-1042-payment-v1"
  },
  "type": "payment_intent.succeeded",
  "data": {
    "object": {
      "id": "pi_TEST3Nabc",
      "object": "payment_intent",
      "amount": 2000,
      "amount_received": 2000,
      "currency": "usd",
      "status": "succeeded",
      "customer": "cus_TEST123abc",
      "metadata": { "order_id": "DRZ-1042" }
    }
  }
}
```

| ফিল্ড | মানে | QA হিসেবে কী দেখবেন |
|---|---|---|
| `id` | ইভেন্টের ইউনিক id, `evt_` দিয়ে শুরু | অ্যাপ কি এটা সংরক্ষণ করে ডুপ্লিকেট চেনে? |
| `type` | কী ঘটেছে, যেমন `payment_intent.succeeded` | অ্যাপ কি সঠিক type-এ সঠিক কাজ করে, অচেনা type-এ ক্র্যাশ করে না? |
| `data.object` | সংশ্লিষ্ট অবজেক্টের স্ন্যাপশট, ইভেন্টের মুহূর্তে | অ্যাপ কি `metadata.order_id` দিয়ে সঠিক অর্ডার খুঁজে পায়? |
| `created` | ইভেন্ট তৈরির সময় (Unix timestamp, সেকেন্ডে) | ইভেন্ট উল্টো ক্রমে এলে অ্যাপ কী করে? |
| `livemode` | `true` হলে Live, `false` হলে Test | Test ইভেন্ট দিয়ে Live অর্ডার আপডেট হয় না তো? |
| `api_version` | কোন API ভার্সনের ফরম্যাটে `data.object` সাজানো | ভার্সন বদলালে ফিল্ডের নাম বদলাতে পারে |
| `data.previous_attributes` | `*.updated` ইভেন্টে কোন ফিল্ড আগে কী ছিল | আপডেট লজিক টেস্টে কাজের |

> [!TIP] ক্রম আর ডুপ্লিকেট
> Stripe ইভেন্ট পাঠানোর **ক্রম নিশ্চিত করে না**, আর একই ইভেন্ট **একাধিকবার** আসতে পারে। যেমন `charge.refunded` কখনো `payment_intent.succeeded`-এর আগে পৌঁছাতে পারে। ভালো অ্যাপ ইভেন্ট id সংরক্ষণ করে, আর দরকারে API থেকে অবজেক্টের সর্বশেষ অবস্থা আবার retrieve করে।

| ইভেন্ট | কখন আসে | অ্যাপের কী করা উচিত |
|---|---|---|
| `payment_intent.succeeded` | PaymentIntent সফলভাবে টাকা নিয়েছে | অর্ডার Paid, স্টক কমানো, রসিদ পাঠানো (যদি Checkout ব্যবহার না করেন বা দুটোর একটাকে মূল ধরেন) |
| `payment_intent.payment_failed` | পেমেন্ট চেষ্টা ব্যর্থ (ডিক্লাইন ইত্যাদি) | অর্ডার Pending/Failed রাখা, গ্রাহককে আবার চেষ্টার সুযোগ, স্টক রিজার্ভ ছেড়ে দেওয়া |
| `checkout.session.completed` | গ্রাহক Checkout শেষ করেছে | `payment_status` দেখে: `paid` হলে অর্ডার পূরণ; `unpaid` হলে (দেরিতে নিশ্চিত হওয়া মেথড) অপেক্ষা |
| `checkout.session.expired` | Session মেয়াদোত্তীর্ণ, পে করা হয়নি | কার্ট বা রিজার্ভ করা স্টক ছেড়ে দেওয়া, চাইলে "কার্টে জিনিস রয়ে গেছে" রিমাইন্ডার |
| `charge.refunded` | চার্জের পুরো বা আংশিক রিফান্ড | অর্ডারের রিফান্ড অবস্থা আপডেট, অ্যাক্সেস বাতিল (পুরো রিফান্ডে), হিসাব মেলানো |
| `charge.dispute.created` | গ্রাহক ব্যাংকে চার্জ নিয়ে আপত্তি (chargeback) তুলেছে | অর্ডার "Disputed", টিমকে অ্যালার্ট, প্রমাণ জোগাড়; সময়সীমা আছে |
| `invoice.paid` | সাবস্ক্রিপশন বা ইনভয়েসের টাকা পরিশোধ | সাবস্ক্রিপশন চালু রাখা বা নবায়ন, মেয়াদ বাড়ানো |

একটা অ্যাপ সব ইভেন্ট শোনে না, শুধু যেগুলো দরকার। যে ইভেন্ট অ্যাপ চেনে না, সেটাও **2xx** দিয়ে গ্রহণ করে নীরবে উপেক্ষা করা ভালো, যাতে Stripe অকারণে retry না করে।

> [!NOTE] একই পেমেন্টে একাধিক ইভেন্ট
> Checkout দিয়ে একটা সফল পেমেন্টে সাধারণত `checkout.session.completed`, `payment_intent.succeeded`, `charge.succeeded` সহ কয়েকটা ইভেন্ট আসে। অ্যাপ যদি দুটোতেই অর্ডার পূরণ করে, তাহলে ডাবল ইমেইল বা ডাবল অ্যাক্সেস হতে পারে। QA হিসেবে দেখুন কোন ইভেন্টকে "মূল" ধরা হয়েছে।

## এন্ডপয়েন্টের সোনালি নিয়ম: দ্রুত 2xx

Stripe ইভেন্ট পাঠিয়ে অপেক্ষা করে আপনার রেসপন্সের জন্য।

- **2xx** (যেমন `200`) পেলে: ডেলিভারি সফল।
- **অন্য কোনো Status Code**, টাইমআউট বা কানেকশন এরর হলে: ব্যর্থ ধরে, পরে আবার পাঠায় (retry)। Live Mode-এ কয়েক দিন ধরে ক্রমবর্ধমান বিরতিতে retry করে; Test Mode-এ retry কম। দীর্ঘ সময় ব্যর্থ হলে Stripe এন্ডপয়েন্ট নিয়ে ইমেইলে সতর্ক করে এবং শেষে নিষ্ক্রিয়ও করতে পারে।

তাই ভালো ডিজাইন:

```text
১. রিকোয়েস্ট এল
২. সিগনেচার যাচাই (না মিললে 400)
৩. evt_ id আগে প্রসেস হয়েছে? হলে 200 দিয়ে শেষ
৪. ইভেন্টটা ডেটাবেস বা queue-তে রাখা
৫. সাথে সাথে 200 ফেরত
৬. ব্যাকগ্রাউন্ডে: ইমেইল, PDF, স্টক আপডেট
```

রিডাইরেক্ট (৩০১/৩০২) দিলেও Stripe ব্যর্থ ধরে। HTTP থেকে HTTPS-এ রিডাইরেক্ট করা এন্ডপয়েন্ট একটা সাধারণ কনফিগারেশন বাগ।

সিগনেচার যাচাই আলাদা লেসনে দেখব: [Webhook সিগনেচার যাচাই](/lessons/webhook-signature-verification/)।

## হাতেকলমে অনুশীলন

এখনো আমরা নিজের সার্ভার বানাইনি; আজ Stripe Dashboard থেকেই ইভেন্ট দেখব।

1. Stripe Dashboard-এ Test Mode / Sandbox চালু আছে নিশ্চিত করুন।
2. [Stripe API টেস্ট](/lessons/stripe-api-testing/) লেসনের মতো Postman থেকে একটা সফল PaymentIntent আর একটা ডিক্লাইন PaymentIntent বানান।
3. Dashboard-এর **Developers / Workbench** অংশে **Events** খুলুন (মেনুর নাম সময়ের সাথে বদলায়; "Events" খুঁজুন)।
4. সফল পেমেন্টের জন্য কোন কোন ইভেন্ট তৈরি হলো তা লিখুন। `payment_intent.created` আর `payment_intent.succeeded` দেখতে পাবেন, সাথে চার্জ-সম্পর্কিত ইভেন্ট।
5. একটা ইভেন্ট খুলে পুরো JSON দেখুন। `type`, `data.object.id`, `data.object.metadata`, `livemode` খুঁজে বের করুন।
6. ডিক্লাইন পেমেন্টের ইভেন্ট দেখুন: `payment_intent.payment_failed`-এর `data.object.last_payment_error`-এ কী আছে?
7. একটা আংশিক রিফান্ড করুন, তারপর `charge.refunded` ইভেন্টের `data.object.amount_refunded` দেখুন।

স্ক্রিনশট বর্ণনা: Events তালিকায় প্রতিটা সারিতে ইভেন্টের type, সংশ্লিষ্ট অবজেক্টের id আর সময়; একটা সারিতে ক্লিক করলে ডান দিকে ইভেন্টের JSON আর (এন্ডপয়েন্ট থাকলে) ডেলিভারির চেষ্টাগুলো দেখা যায়।

> [!CHECK] সফলতার চেকলিস্ট
> - সফল আর ব্যর্থ পেমেন্টের ইভেন্টের পার্থক্য বলতে পারছেন
> - Event JSON থেকে `evt_` id, type আর order_id বের করতে পারছেন
> - বলতে পারছেন কেন success পেজ নয়, Webhook-ই অর্ডার Paid করার ভিত্তি

> [!MISTAKE] সাধারণ ভুল
> - success পেজ লোড হলেই অর্ডার Paid করা।
> - Webhook-এ সব ভারী কাজ শেষ করে তারপর ২০০ দেওয়া, ফলে টাইমআউট আর retry।
> - ধরে নেওয়া যে ইভেন্ট সঠিক ক্রমে আর ঠিক একবার আসবে।
> - অচেনা ইভেন্ট type-এ ৫০০ এরর দেওয়া।
> - Test Mode-এর ইভেন্ট (`livemode: false`) দিয়ে প্রোডাকশন ডেটা আপডেট হতে দেওয়া।

## সারসংক্ষেপ

- Webhook মানে ঘটনা ঘটলে Stripe নিজেই আপনার সার্ভারের URL-এ POST পাঠায়; Polling-এর চেয়ে দ্রুত ও কম অপচয়ী।
- success পেজ শুধু UX; অর্ডার Paid করার ভিত্তি Webhook বা সার্ভার-সাইড API যাচাই।
- Event অবজেক্টে `id`, `type`, `data.object`, `created`, `livemode`, `api_version` সবচেয়ে গুরুত্বপূর্ণ।
- ইভেন্ট ডুপ্লিকেট বা উল্টো ক্রমে আসতে পারে; অ্যাপকে তা সামলাতে হবে।
- এন্ডপয়েন্ট দ্রুত 2xx দেবে, ভারী কাজ ব্যাকগ্রাউন্ডে।
