পেমেন্ট সিস্টেমে সবচেয়ে ভয়ংকর বাগগুলোর একটা হলো **ডাবল চার্জ**: গ্রাহক একবার কিনেছে, টাকা কেটেছে দুবার। এরপর আসে রাগী ফোনকল, রিফান্ড, আর ব্র্যান্ডের ক্ষতি।

এই লেসনে শিখব কীভাবে **Idempotency** (একই রিকোয়েস্ট বারবার পাঠালেও ফল একবারই হবে) এই সমস্যা আটকায়, আর QA হিসেবে কীভাবে তা টেস্ট করবেন।

## এই লেসনে যা শিখবেন

- Idempotency আর Idempotency Key কী, সহজ উদাহরণসহ
- কেন পেমেন্টে এটা অপরিহার্য: টাইমআউট, retry, ডাবল ক্লিক
- Stripe-এর `Idempotency-Key` হেডারের আচরণের নিয়ম
- Postman-এ ধাপে ধাপে Idempotency টেস্ট
- নিজের অ্যাপের ডাবল-সাবমিট সুরক্ষা কীভাবে যাচাই করবেন
- একটা রেডিমেড টেস্ট কেস টেবিল

## Idempotency কী: একটা দেশি উদাহরণ

ভাবুন আপনি লিফটে উঠে ৫ তলার বাটন চাপলেন। লিফট আসতে দেরি করছে, তাই অধৈর্য হয়ে আরও ৪ বার চাপলেন। লিফট কি ৫ বার ৫ তলায় যাবে? না, একবারই যাবে। লিফটের বাটন **idempotent**।

এবার উল্টো উদাহরণ। আপনি bKash-এ "Send Money" করলেন, নেটওয়ার্ক আটকে গেল, স্ক্রিনে কিছু এল না। আবার পাঠালেন। যদি সিস্টেম idempotent না হয়, তাহলে বন্ধু দুবার টাকা পাবে আর আপনার অ্যাকাউন্ট থেকে দুবার কাটবে।

**Idempotency Key** হলো একটা ইউনিক টোকেন (সাধারণত UUID), যেটা ক্লায়েন্ট রিকোয়েস্টের সাথে পাঠায়। সার্ভার মনে রাখে: "এই কী দিয়ে আগে কী করেছিলাম আর কী উত্তর দিয়েছিলাম।" একই কী আবার এলে কাজটা দ্বিতীয়বার না করে আগের উত্তরটাই ফেরত দেয়।

> [!NOTE] HTTP মেথড আর Idempotency
> HTTP-র নিয়ম অনুযায়ী GET, PUT, DELETE স্বভাবগতভাবে idempotent। কিন্তু POST নয়: প্রতিটা POST সাধারণত নতুন কিছু তৈরি করে। পেমেন্ট তৈরি হয় POST দিয়ে, তাই সেখানেই Idempotency Key দরকার। HTTP-র বেসিক মনে না থাকলে [HTTP ও JSON বেসিক](/lessons/http-json-basics/) দেখে নিন।

## কেন পেমেন্টে Idempotency অপরিহার্য

### পরিস্থিতি ১: টাইমআউটের পর retry

একটা রাইড অ্যাপ ট্রিপ শেষে সার্ভার থেকে Stripe-এ চার্জ পাঠাল। Stripe টাকা কেটে নিল, কিন্তু রেসপন্স ফেরার পথে নেটওয়ার্ক কেটে গেল। অ্যাপের কাছে খবর: "টাইমআউট"।

অ্যাপ জানে না টাকা কেটেছে কি না। নিরাপদ উপায় হলো **একই Idempotency Key দিয়ে আবার পাঠানো**। টাকা কেটে থাকলে Stripe আগের ফলটাই দেবে; না কাটলে এবার কাটবে। দুই ক্ষেত্রেই ঠিক একবার।

### পরিস্থিতি ২: ডাবল ক্লিক ও ডাবল সাবমিট

একটা কোর্স-বিক্রির সাইটে ধীর ইন্টারনেটে গ্রাহক "Pay ৳২৫০০" বাটনে চাপলেন। কিছু হচ্ছে না দেখে আবার চাপলেন। অথবা পেজ রিফ্রেশ করলেন, অথবা দুই ট্যাবে একই চেকআউট খোলা ছিল।

### পরিস্থিতি ৩: অটো retry

অনেক HTTP লাইব্রেরি আর Stripe-এর অফিসিয়াল SDK নেটওয়ার্ক এরর হলে নিজে থেকে retry করে। Stripe SDK এই retry-গুলোতে স্বয়ংক্রিয়ভাবে Idempotency Key যোগ করে। কিন্তু আপনার নিজের লেখা কোড বা queue worker retry করলে কী দেওয়া হচ্ছে কি না, সেটা QA-কে যাচাই করতে হবে।

| সমস্যা | Idempotency ছাড়া | Idempotency সহ |
|---|---|---|
| টাইমআউটের পর retry | ডাবল চার্জের ঝুঁকি | একবার চার্জ, একই id ফেরত |
| ডাবল ক্লিক (সার্ভারে একই কী) | দুটো পেমেন্ট | একটা পেমেন্ট |
| queue worker দুবার একই জব চালাল | দুটো রিফান্ড | একটা রিফান্ড |

## Stripe-এর Idempotency-Key হেডার: নিয়মগুলো

Stripe-এ যেকোনো POST রিকোয়েস্টে একটা হেডার যোগ করলেই হয়:

```bash
curl https://api.stripe.com/v1/payment_intents \
  -H "Authorization: Bearer sk_test_XXXXXXXXXXXXXXXX" \
  -H "Idempotency-Key: order-DRZ-1042-payment-v1" \
  -d amount=2000 \
  -d currency=usd \
  -d "metadata[order_id]=DRZ-1042"
```

Stripe-এর অফিসিয়াল আচরণ (বিস্তারিত: https://docs.stripe.com/api/idempotent_requests):

| পরিস্থিতি | Stripe কী করে |
|---|---|
| একই কী + একই প্যারামিটার, আবার পাঠানো | প্রথমবারের **সেভ করা রেসপন্স** ফেরত দেয় (একই Status Code, একই বডি, একই `pi_` id)। নতুন অবজেক্ট তৈরি হয় না। |
| প্রথম রিকোয়েস্ট এরর দিয়েছিল (যেমন ডিক্লাইন) | একই কী-তে আবার পাঠালে সেই একই এরর ফেরত আসে, কারণ ফলাফলটাই সেভ হয়েছে |
| একই কী + **ভিন্ন** প্যারামিটার | এরর দেয় (`idempotency_error`): কী শুধু প্রথমবারের প্যারামিটারের সাথেই ব্যবহার করা যায় |
| প্রথম রিকোয়েস্ট এখনো চলছে, এমন সময় একই কী আবার এল | কনফ্লিক্ট এরর (৪০৯) দেয়; পরে retry করতে হয় |
| নতুন কী | সম্পূর্ণ নতুন রিকোয়েস্ট, নতুন অবজেক্ট |
| কী-এর বয়স ২৪ ঘণ্টার বেশি | Stripe কী মুছে ফেলতে পারে; তখন একই কী নতুন রিকোয়েস্ট হিসেবে চলে |
| GET বা DELETE-এ কী পাঠানো | কোনো প্রভাব নেই; এগুলো এমনিতেই idempotent। Idempotency Key শুধু POST-এর জন্য। |

> [!TIP] রিপ্লে চেনার উপায়
> সেভ করা রেসপন্স ফেরত এলে Stripe সাধারণত রেসপন্স হেডারে `Idempotent-Replayed: true` দেয়। Postman-এর Headers ট্যাবে এটা খুঁজুন। প্রথম রিকোয়েস্টে এটা থাকবে না।

আরেকটা সূক্ষ্ম কথা: রিকোয়েস্ট যদি একদম শুরুতেই প্যারামিটার যাচাইয়ে ব্যর্থ হয় (যেমন `amount` নেই), Stripe সাধারণত সেই ফল সেভ করে না। তখন ভুল ঠিক করে একই কী দিয়ে আবার পাঠানো যায়।

### ভালো Idempotency Key কেমন হয়

- প্রতিটা **লজিক্যাল অপারেশনের** জন্য একটা কী। যেমন "অর্ডার DRZ-1042-এর পেমেন্ট"।
- UUID v4 সবচেয়ে প্রচলিত। অথবা অর্ডার id থেকে বানানো কী।
- সর্বোচ্চ ২৫৫ অক্ষর।
- কী-তে ইমেইল, ফোন নম্বর বা অন্য ব্যক্তিগত তথ্য রাখবেন না।
- retry-তে **একই** কী, নতুন অপারেশনে **নতুন** কী।

## Postman-এ হাতেকলমে Idempotency টেস্ট

আগের লেসনের [Stripe API Practice](/lessons/stripe-api-testing/) Collection-এ একটা নতুন ফোল্ডার বানান: **Idempotency**।

### ধাপ ১: একটা কী জেনারেট করুন

Postman-এ `{{$guid}}` একটা ডাইনামিক ভেরিয়েবল, প্রতিবার নতুন UUID দেয়। কিন্তু আমাদের দরকার একই কী দুবার। তাই Pre-request Script-এ একবার বানিয়ে সেভ করুন:

```js
// "Create PI (first)" রিকোয়েস্টের Pre-request Script
pm.collectionVariables.set("idem_key", pm.variables.replaceIn("{{$guid}}"));
```

### ধাপ ২: প্রথম রিকোয়েস্ট

POST `{{base_url}}/v1/payment_intents`, হেডার `Idempotency-Key: {{idem_key}}`, বডি `amount=2000`, `currency=usd`, `payment_method=pm_card_visa`, `confirm=true`, `automatic_payment_methods[enabled]=true`, `automatic_payment_methods[allow_redirects]=never`।

```js
// Tests
const body = pm.response.json();
pm.test("200", () => pm.response.to.have.status(200));
pm.collectionVariables.set("first_pi", body.id);
pm.test("Not a replay", () => pm.expect(pm.response.headers.get("Idempotent-Replayed")).to.not.eql("true"));
```

### ধাপ ৩: একই কী, একই বডি

রিকোয়েস্টটা Duplicate করে নাম দিন "Create PI (replay)"। Pre-request Script মুছে দিন, যাতে কী না বদলায়।

```js
// Tests
const body = pm.response.json();
pm.test("Same PaymentIntent id", () => pm.expect(body.id).to.eql(pm.collectionVariables.get("first_pi")));
pm.test("Replayed header", () => pm.expect(pm.response.headers.get("Idempotent-Replayed")).to.eql("true"));
```

### ধাপ ৪: একই কী, ভিন্ন বডি

আবার Duplicate করে `amount=5000` দিন, কী একই।

```js
pm.test("Rejected", () => pm.expect(pm.response.code).to.be.within(400, 499));
const err = pm.response.json().error;
pm.test("idempotency_error", () => pm.expect(err.type).to.eql("idempotency_error"));
```

### ধাপ ৫: নতুন কী

একই বডি, কিন্তু হেডারে `{{$guid}}` সরাসরি। এবার **নতুন** `pi_` id আসবে। Dashboard-এর Payments পেজে গিয়ে দেখুন এখন ২টা পেমেন্ট আছে: প্রথম আর এই নতুনটা। replay-গুলো নতুন পেমেন্ট বানায়নি।

### ধাপ ৬: ডিক্লাইন রিপ্লে

নতুন কী দিয়ে `pm_card_chargeDeclined` পাঠান (৪০২)। একই কী-তে আবার পাঠান। একই ৪০২ আর একই এরর বডি আসবে, যদিও আপনি "ভাবছেন" এবার হয়তো অন্য ফল হবে। এটাই সেভ করা রেসপন্সের মানে।

> [!CHECK] সফলতার চেকলিস্ট
> - replay-তে একই `pi_` id আর `Idempotent-Replayed: true`
> - ভিন্ন প্যারামিটারে `idempotency_error`
> - নতুন কী-তে নতুন id
> - Dashboard-এ পেমেন্টের সংখ্যা আপনার হিসাবের সাথে মেলে

## নিজের অ্যাপের ডাবল-সাবমিট সুরক্ষা টেস্ট

Stripe-এর Idempotency তখনই কাজে লাগে যখন **আপনার অ্যাপ** সঠিকভাবে কী পাঠায়। তাই আসল টেস্ট হলো আপনার অ্যাপ। একটা ভালো অ্যাপে সুরক্ষা থাকে কয়েক স্তরে:

| স্তর | কী করে | কীভাবে টেস্ট করবেন |
|---|---|---|
| ফ্রন্টএন্ড: বাটন disable | প্রথম ক্লিকের পর বাটন বন্ধ, লোডিং দেখায় | DevTools-এ Network throttling "Slow 3G" দিয়ে দ্রুত কয়েকবার ক্লিক |
| সার্ভার: Idempotency Key | অর্ডারের জন্য একটা কী বানিয়ে সংরক্ষণ, retry-তে একই কী | সার্ভার লগে বা Stripe Dashboard-এর রিকোয়েস্ট লগে দেখুন দুই রিকোয়েস্টে একই কী কি না |
| সার্ভার: ডিডুপ চেক | "এই অর্ডার কি আগেই পেইড বা প্রসেসিং?" চেক করে | Postman থেকে একই চেকআউট এন্ডপয়েন্টে একসাথে ২টা রিকোয়েস্ট |
| ডেটাবেস: unique constraint | একই order_id-তে দুটো payment রো ঢুকতে দেয় না | সমান্তরাল রিকোয়েস্টের পর DB-তে রো গুনুন |

> [!TIP] সমান্তরাল রিকোয়েস্ট পাঠানোর সহজ উপায়
> নিজের লোকাল অ্যাপে (কখনো অন্যের সাইটে নয়) দুটো curl একসাথে চালাতে পারেন:
> `curl ... & curl ... & wait` — দুটো রিকোয়েস্ট প্রায় একই মুহূর্তে যায়।

```bash
# শুধু নিজের লোকাল অ্যাপে: একই অর্ডারের চেকআউট দুবার একসাথে
curl -X POST http://localhost:3000/checkout -d order_id=TEST-1001 &
curl -X POST http://localhost:3000/checkout -d order_id=TEST-1001 &
wait
```

তারপর যাচাই করুন: Stripe Dashboard-এ ঐ অর্ডারের metadata দিয়ে কয়টা PaymentIntent? আপনার ডেটাবেসে কয়টা payment রো? উত্তর অবশ্যই ১।

ব্রাউজারের **Back** বাটন, পেজ **রিফ্রেশ**, আর **দুই ট্যাবে** একই চেকআউট খুলে দুটোতেই পে করা — এগুলোও ক্লাসিক টেস্ট।

## টেস্ট কেস টেবিল

| ID | সিনারিও | ধাপ | প্রত্যাশিত ফল |
|---|---|---|---|
| IDM-01 | একই কী, একই প্যারামিটার | POST দুবার | একই id, দ্বিতীয়টায় `Idempotent-Replayed: true`, Dashboard-এ ১টা পেমেন্ট |
| IDM-02 | একই কী, ভিন্ন amount | প্রথমে ২০০০, পরে ৫০০০ | দ্বিতীয়টায় `idempotency_error` |
| IDM-03 | নতুন কী, একই প্যারামিটার | POST দুবার, ভিন্ন কী | দুটো ভিন্ন id (প্রত্যাশিত, তাই অ্যাপকে কী ঠিকমতো পুনঃব্যবহার করতে হবে) |
| IDM-04 | ডিক্লাইন রিপ্লে | ডিক্লাইন কার্ড, একই কী-তে দুবার | দুবারই একই ৪০২ বডি |
| IDM-05 | রিফান্ডে Idempotency | POST /v1/refunds একই কী-তে দুবার | ১টা রিফান্ড, একই `re_` id |
| IDM-06 | ভ্যালিডেশন এরর তারপর ঠিক করা | `amount` ছাড়া পাঠান, তারপর একই কী-তে ঠিক বডি | দ্বিতীয়টা সফল হওয়া উচিত (প্রথমটার ফল সেভ হয়নি) |
| IDM-07 | অ্যাপে ডাবল ক্লিক | Slow 3G, দ্রুত ৩ ক্লিক | ১টা অর্ডার, ১টা চার্জ |
| IDM-08 | অ্যাপে সমান্তরাল রিকোয়েস্ট | একই order_id-তে ২টা curl একসাথে | ১টা PaymentIntent, DB-তে ১টা রো |
| IDM-09 | রিফ্রেশ / Back | পে করার পর রিফ্রেশ বা Back করে আবার পে | দ্বিতীয় চার্জ হয় না, "ইতিমধ্যে পরিশোধিত" বার্তা |
| IDM-10 | worker retry | ব্যাকগ্রাউন্ড জব ফেইল করিয়ে retry (ডেভ টিমের সাহায্যে) | retry-তে একই কী, নতুন চার্জ নয় |

> [!MISTAKE] সাধারণ ভুল
> - প্রতিটা retry-তে নতুন UUID বানানো। তাহলে Idempotency কোনো কাজই করে না।
> - শুধু ফ্রন্টএন্ডে বাটন disable করে নিশ্চিন্ত হওয়া। সার্ভারে সুরক্ষা না থাকলে Postman বা দুই ট্যাব দিয়ে সহজেই ভাঙা যায়।
> - ভাবা যে Stripe কী চিরকাল মনে রাখে। ২৪ ঘণ্টার বেশি পুরনো কী-র উপর নির্ভর করা যায় না।
> - GET রিকোয়েস্টে Idempotency Key দিয়ে টেস্ট করে "কাজ করছে" ধরে নেওয়া। GET এমনিতেই নতুন কিছু বানায় না।
> - একই কী অন্য অর্ডারে ভুল করে ব্যবহার, যেমন কী হিসেবে শুধু ইউজার id দেওয়া।

## সারসংক্ষেপ

- Idempotency মানে একই অপারেশন বারবার চালালেও ফল একবারই।
- পেমেন্টে টাইমআউট, retry আর ডাবল ক্লিক ডাবল চার্জের মূল কারণ।
- Stripe-এ POST-এ `Idempotency-Key` হেডার দিন; একই কী + একই প্যারামিটার = সেভ করা রেসপন্স, ভিন্ন প্যারামিটার = এরর।
- কী অন্তত ২৪ ঘণ্টা থাকে; দীর্ঘমেয়াদি ডিডুপ অ্যাপের ডেটাবেসের দায়িত্ব।
- নিজের অ্যাপে কয়েক স্তরের সুরক্ষা টেস্ট করুন: বাটন disable, সার্ভার কী, ডিডুপ, unique constraint।

2. IDM-07 ব্যর্থ হলে কেমন বাগ রিপোর্ট লিখবেন? শিরোনাম, ধাপ, প্রত্যাশিত বনাম আসল ফল, আর Severity লিখুন ([পেমেন্ট বাগ রিপোর্ট](/lessons/payment-bug-reports/) দেখুন)।
