Webhook "একবার কাজ করেছে" মানেই কাজ শেষ নয়। বাস্তবে ইভেন্ট দুইবার আসে, উল্টো ক্রমে আসে, দেরিতে আসে, আবার কখনো আসেই না। একজন ভালো পেমেন্ট QA এই সব অস্বাভাবিক অবস্থা আগে থেকে টেস্ট করেন।

এই লেসনে আমরা একটি পূর্ণ Webhook টেস্ট কেস টেবিল বানাব, তারপর সাপোর্ট টিমের সবচেয়ে কমন অভিযোগ "পেমেন্ট সফল কিন্তু অ্যাপে অ্যাক্সেস নেই" কীভাবে ধাপে ধাপে খুঁজে বের করবেন, সেটা শিখব।

## এই লেসনে যা শিখবেন

- ডুপ্লিকেট ইভেন্ট আর আউট-অফ-অর্ডার ডেলিভারি কেন হয় এবং কীভাবে টেস্ট করবেন
- Stripe-এর রিট্রাই আচরণ: কোন রেসপন্সে রিট্রাই হয়, কতদিন পর্যন্ত
- টাইমআউট, ভুল সিগনেচার, পুরনো টাইমস্ট্যাম্প, অজানা ইভেন্ট আর ডিসেবল এন্ডপয়েন্টের টেস্ট
- একটি রেডি টেস্ট কেস টেবিল যা নিজের প্রজেক্টে কপি করবেন
- "পেমেন্ট সফল কিন্তু অ্যাক্সেস নেই" সমস্যার Decision Flow (ধাপে ধাপে সিদ্ধান্তের পথ)

## Webhook কেন "অগোছালো" হয়

একটা উপমা দিই। ধরুন Daraz-এর মতো একটি শপ থেকে আপনার কাছে কুরিয়ারে তিনটি চিঠি আসবে: "অর্ডার হয়েছে", "পেমেন্ট হয়েছে", "প্যাক হয়েছে"। কুরিয়ার কখনো দ্বিতীয় চিঠি আগে দেয়, কখনো একই চিঠি দুইবার দেয়, আপনি বাসায় না থাকলে পরে আবার আসে।

Stripe Webhook-ও ঠিক এমন। Stripe-এর ডকুমেন্টেশন স্পষ্ট বলে:

- **ক্রমের গ্যারান্টি নেই**: ইভেন্ট যে ক্রমে তৈরি হয়েছে, সেই ক্রমে পৌঁছাবে এমন নিশ্চয়তা নেই
- **একাধিকবার আসতে পারে**: একই ইভেন্ট (একই `evt_` আইডি) একাধিকবার আসতে পারে
- **রিট্রাই হয়**: আপনার সার্ভার 2xx না দিলে Stripe পরে আবার চেষ্টা করে

তাই অ্যাপকে এমনভাবে বানাতে হয় যাতে এই সব অবস্থাতেও ফল ঠিক থাকে। আর QA-এর কাজ সেটা প্রমাণ করা।

### ডুপ্লিকেট ইভেন্ট

একই `event.id` দুইবার এলে অ্যাপ যেন দুইবার কাজ না করে। যেমন দুইবার কোর্স অ্যাক্সেস দেওয়া হয়তো ক্ষতিকর নয়, কিন্তু দুইবার ওয়ালেটে ক্যাশব্যাক যোগ করা বা দুইবার ইনভয়েস ইমেইল পাঠানো স্পষ্ট বাগ।

এর সমাধান Idempotency (একই জিনিস বারবার এলেও ফল একবারই হবে), যা আমরা [Signature Verification লেসনে](/lessons/webhook-signature-verification/) কোডে দেখেছি।

### আউট-অফ-অর্ডার ডেলিভারি

কয়েকটি বাস্তব উদাহরণ:

- `payment_intent.succeeded` এল `checkout.session.completed`-এর আগে। অ্যাপ যদি Checkout Session থেকে অর্ডার তৈরি করে, তাহলে PaymentIntent ইভেন্টের সময় অর্ডারই খুঁজে পাবে না
- `charge.refunded` এল, কিন্তু সেই পেমেন্টের `payment_intent.succeeded` এখনো প্রসেস হয়নি। অ্যাপ হয়তো পরে succeeded প্রসেস করে অর্ডারকে আবার "paid" বানিয়ে দেবে, অথচ টাকা ফেরত গেছে
- সাবস্ক্রিপশনে `customer.subscription.updated` (প্ল্যান বদল) এল `customer.subscription.created`-এর আগে

ভালো ডিজাইন হলো: ইভেন্টকে "কিছু বদলেছে" এমন সংকেত হিসেবে নেওয়া, তারপর দরকার হলে Stripe API থেকে অবজেক্টের সর্বশেষ অবস্থা পড়া। আরেকটা উপায় হলো স্টেট মেশিন: "refunded" অবস্থা থেকে "paid"-এ ফেরত যাওয়া নিষেধ।

> [!TIP] কীভাবে উল্টো ক্রম টেস্ট করবেন
> Stripe CLI দিয়ে ইভেন্ট সবসময় আসল ক্রমে আসবে না, আবার ইচ্ছামতো ক্রমও বানানো কঠিন। লোকাল ল্যাবে আগে একটি আসল ইভেন্টের JSON সেভ করুন (`stripe listen` আউটপুট বা Dashboard থেকে), তারপর নিজের লোকাল সিক্রেট দিয়ে সাইন করে ইচ্ছামতো ক্রমে পাঠান। Dashboard-এর "Resend" বাটন দিয়েও পুরনো ইভেন্ট আবার পাঠানো যায়।

### Stripe-এর রিট্রাই আচরণ

আপনার এন্ডপয়েন্ট 2xx ছাড়া অন্য কিছু দিলে (4xx, 5xx, কানেকশন এরর, টাইমআউট), Stripe ডেলিভারিকে ব্যর্থ ধরে।

- **Live Mode**: Stripe এক্সপোনেনশিয়াল ব্যাকঅফে (প্রতিবার আগের চেয়ে বেশি অপেক্ষা করে) **৩ দিন পর্যন্ত** আবার পাঠানোর চেষ্টা করে
- **Test Mode**: Test Mode-এ রিট্রাই কম/ভিন্ন হতে পারে, ডকুমেন্টেশন দেখুন
- Dashboard-এ প্রতিটি ইভেন্টের delivery attempts, রেসপন্স কোড আর পরের চেষ্টার সময় দেখা যায়
- অনেক দিন ধরে ধারাবাহিকভাবে ব্যর্থ হলে Stripe এন্ডপয়েন্ট ডিসেবল করে দিতে পারে এবং অ্যাকাউন্টের মালিককে ইমেইলে জানায়

বিস্তারিত ও সর্বশেষ নিয়ম: [Stripe Docs: Webhooks](https://docs.stripe.com/webhooks), সেখানে "retry" লিখে খুঁজুন।

> [!NOTE]
> এর মানে একটা গুরুত্বপূর্ণ জিনিস: ৪০০ দিলেও রিট্রাই হয়। তাই সিগনেচার মিসম্যাচ হলে সমস্যা ঠিক না হওয়া পর্যন্ত ব্যর্থতা জমতে থাকে। ঠিক করার পর Dashboard থেকে ব্যর্থ ইভেন্ট Resend করা যায়।

### টাইমআউট

ধরুন হ্যান্ডলার প্রথমে PDF ইনভয়েস বানায়, তারপর তিনটি ইমেইল পাঠায়, তারপর ২০০ দেয়। এতে অনেক সেকেন্ড লেগে যায়। Stripe ততক্ষণ অপেক্ষা না করে টাইমআউট ধরে নেয় এবং পরে রিট্রাই করে। অথচ আপনার সার্ভার কাজটা শেষ করেছে। ফল: ডুপ্লিকেট প্রসেসিং।

নিয়ম: ভেরিফাই করুন, ইভেন্ট সেভ করুন বা কিউতে দিন, সাথে সাথে ২০০ দিন। ভারী কাজ পরে ব্যাকগ্রাউন্ডে।

| WH-02 | ডুপ্লিকেট ইভেন্ট | একই `evt_` আইডি দুইবার পাঠান (Dashboard Resend বা নিজে সাইন করা) | দ্বিতীয়বার 200, কিন্তু কোনো নতুন কাজ নয় |
| WH-03 | উল্টো ক্রম: PI আগে, Checkout পরে | `payment_intent.succeeded` আগে, `checkout.session.completed` পরে পাঠান | শেষে অর্ডার paid, ডেটা হারায় না, এরর নেই |
| WH-04 | উল্টো ক্রম: refund আগে | `charge.refunded` আগে, `payment_intent.succeeded` পরে | শেষ অবস্থা refunded, paid-এ ফেরত যায় না |
| WH-05 | এন্ডপয়েন্ট 5xx দেয় | হ্যান্ডলারে ইচ্ছা করে `res.status(500)` দিন | Stripe রিট্রাই করে; ঠিক করার পর ইভেন্ট সফল হয় |
| WH-06 | ধীর হ্যান্ডলার (টাইমআউট) | হ্যান্ডলারে ৩০ সেকেন্ড `setTimeout` দিয়ে পরে 200 | Stripe টাইমআউট ধরে; দ্বিতীয় ডেলিভারিতে ডুপ্লিকেট কাজ হয় না |
| WH-07 | ভুল সিগনেচার | curl দিয়ে নকল `Stripe-Signature` | 400, কোনো কাজ নয় |
| WH-08 | পুরনো টাইমস্ট্যাম্প (Replay) | ১০ মিনিট পুরনো `t` দিয়ে নিজে সাইন করা | 400 (tolerance), কোনো কাজ নয় |
| WH-09 | অজানা ইভেন্ট টাইপ | `stripe trigger customer.created` | 200, ইগনোর, লগে "unhandled" |
| WH-10 | এন্ডপয়েন্ট ডিসেবল | Dashboard-এ টেস্ট এন্ডপয়েন্ট Disable করে পেমেন্ট করুন | কোনো ডেলিভারি নেই; অ্যাপে অর্ডার pending থাকে; মনিটরিং অ্যালার্ট দেয় |
| WH-11 | সার্ভার ডাউন | সার্ভার বন্ধ রেখে `stripe trigger` | CLI-তে কানেকশন এরর; সার্ভার চালুর পর Resend করলে সফল |
| WH-12 | ভুল সিক্রেট কনফিগ | `.env`-এ অন্য whsec | সব ইভেন্টে 400; লগে signature error |
| WH-13 | ফেইলড পেমেন্ট | `stripe trigger payment_intent.payment_failed` | 200, অর্ডার failed, অ্যাক্সেস নয় |
| WH-14 | মেটাডেটা নেই | metadata ছাড়া PaymentIntent তৈরি করে সফল করুন | 200, কিন্তু অ্যাপ এরর লগ করে ও অ্যালার্ট দেয়, ভুল ইউজারকে অ্যাক্সেস দেয় না |

### ধাপগুলো সংক্ষেপে

1. দুইটি টার্মিনালে `stripe listen --forward-to localhost:4242/webhook` আর সার্ভার চালু করুন
2. WH-01 দিয়ে বেসলাইন নিশ্চিত করুন: `[200]` আর লগে succeeded
3. Stripe Dashboard (Test Mode) → Developers → Events থেকে একটি ইভেন্ট খুলুন। স্ক্রিনশট বর্ণনা: ইভেন্টের পেজে উপরে টাইপ ও আইডি, নিচে JSON ডেটা, আর ডানে বা নিচে Webhook ডেলিভারির তালিকা ও রেসপন্স কোড
4. WH-05 আর WH-06-এর জন্য কোডে সাময়িক পরিবর্তন করুন, টেস্ট শেষে ফিরিয়ে দিন
5. WH-07 ও WH-08 আগের লেসনের curl আর openssl কমান্ড দিয়ে করুন
6. প্রতিটি ব্যর্থতার জন্য একটি বাগ রিপোর্ট লিখুন

```csv
id,scenario,expected,actual,status
WH-01,normal success,200 order paid,200 order paid,PASS
WH-02,duplicate event,second 200 no side effect,second email sent,FAIL
WH-07,wrong signature,400 no side effect,400,PASS
```

> - অন্তত একটি ডুপ্লিকেট আর একটি উল্টো ক্রমের কেস চালিয়েছেন
> - Dashboard-এ delivery attempts ও রেসপন্স কোড কোথায় দেখায় জানেন

## রুট-কজ গাইড: "পেমেন্ট সফল কিন্তু অ্যাপে অ্যাক্সেস নেই"

এটা পেমেন্ট সাপোর্টের সবচেয়ে কমন টিকিট। একটা কোর্স সাইটে কাস্টমার বলছেন: "কার্ড দিয়ে পেমেন্ট দিলাম, ব্যাংক থেকে SMS-ও এসেছে, টাকা কেটেছে, কিন্তু কোর্স খোলেনি।"

অনুমান না করে, উপর থেকে নিচে একটা একটা ধাপ মিলিয়ে দেখুন। প্রতিটি ধাপে একটি প্রশ্ন, আর উত্তর অনুযায়ী পরের ধাপ।

### ধাপ ১: Stripe Dashboard-এ পেমেন্ট কি সত্যিই সফল?

- কাস্টমারের ইমেইল, সময় বা পরিমাণ দিয়ে Payments-এ খুঁজুন
- স্ট্যাটাস **Succeeded** না হলে (যেমন Incomplete, Requires action, Failed): সমস্যা পেমেন্টে, অ্যাপে নয়। হয়তো 3D Secure শেষ হয়নি বা ব্যাংক ধরে রেখেছে (pending authorization)
- Succeeded হলে: ধাপ ২-এ যান

### ধাপ ২: সংশ্লিষ্ট ইভেন্ট কি তৈরি হয়েছে?

- পেমেন্টের পেজ থেকে Events দেখুন, বা Developers → Events-এ PaymentIntent আইডি দিয়ে খুঁজুন
- আপনার অ্যাপ যে ইভেন্টে অ্যাক্সেস দেয় (যেমন `checkout.session.completed`) সেটি আছে কিনা দেখুন
- আছে: ধাপ ৩

### ধাপ ৩: Webhook delivery attempts আর রেসপন্স কোড কী বলছে?

এই ধাপই সবচেয়ে বেশি তথ্য দেয়:

| যা দেখছেন | মানে | পরের ধাপ |
| --- | --- | --- |
| আপনার এন্ডপয়েন্টে কোনো ডেলিভারিই নেই | এন্ডপয়েন্ট এই ইভেন্টে সাবস্ক্রাইব করা নেই, ভুল মোড বা ডিসেবল | ধাপ ৫ |
| 400 | অ্যাপ রিকোয়েস্ট প্রত্যাখ্যান করেছে, প্রায়ই সিগনেচার | ধাপ ৪ |
| 500 / 502 / 503 | হ্যান্ডলারে এরর বা সার্ভার ডাউন | ধাপ ৬ |
| Timed out | হ্যান্ডলার খুব ধীর | ধাপ ৬ |
| 200 | ডেলিভারি সফল, সমস্যা পরের দিকে | ধাপ ৭ |

### ধাপ ৪: অ্যাপ লগ আর Signature Secret মিসম্যাচ

- অ্যাপ লগে ওই সময়ের "signature verification failed" খুঁজুন
- সবচেয়ে কমন কারণ: **CLI বনাম Dashboard whsec**। ডেভেলপার লোকালে `stripe listen`-এর whsec দিয়ে টেস্ট করেছেন, সেটাই স্টেজিং বা প্রোডাকশনের কনফিগে চলে গেছে। অথচ সেখানে Dashboard এন্ডপয়েন্টের whsec দরকার
- Test Mode আর Live Mode-এর এন্ডপয়েন্ট সিক্রেটও আলাদা
- আরেকটি কারণ: নতুন ডিপ্লয়ে কেউ `express.json()` বা অন্য বডি পার্সার Webhook রুটের আগে বসিয়েছেন

### ধাপ ৫: ভুল ইভেন্ট সাবস্ক্রাইব করা বা ভুল এন্ডপয়েন্ট

- Dashboard → Webhooks-এ এন্ডপয়েন্টের URL ঠিক কিনা দেখুন (staging বনাম production, শেষে স্ল্যাশ, http বনাম https)
- এন্ডপয়েন্টটি সঠিক ইভেন্ট শুনছে কিনা: যেমন অ্যাপ `checkout.session.completed` আশা করছে, কিন্তু সাবস্ক্রাইব করা শুধু `payment_intent.succeeded`
- এন্ডপয়েন্ট Disabled কিনা

### ধাপ ৬: হ্যান্ডলারের এরর

- 5xx হলে অ্যাপের এরর লগ বা স্ট্যাক ট্রেস দেখুন: null reference, DB কানেকশন, নতুন ফিল্ড যা কোড আশা করেনি
- টাইমআউট হলে হ্যান্ডলারে কোন অংশ ধীর (ইমেইল, PDF, বাইরের API কল) খুঁজুন

### ধাপ ৭: DB আর ইউজার ম্যাপিং (metadata)

২০০ এসেছে, লগে "processed"। তবু অ্যাক্সেস নেই? তাহলে প্রশ্ন: **কোন ইউজারের** অর্ডার আপডেট হলো?

- Checkout Session বা PaymentIntent তৈরির সময় অ্যাপ সাধারণত `metadata`-তে `user_id` বা `order_id` পাঠায়। ইভেন্টের JSON-এ সেটা আছে কিনা, সঠিক কিনা দেখুন
- কাস্টমার হয়তো অন্য ইমেইল দিয়ে চেকআউট করেছেন, আর অ্যাপ ইমেইল দিয়ে ইউজার খোঁজে
- DB-তে অর্ডারের স্ট্যাটাস সত্যিই "paid" হয়েছে কিনা, আর অ্যাক্সেস টেবিলে এন্ট্রি আছে কিনা

### ধাপ ৮: ক্যাশিং

- DB-তে সব ঠিক, কিন্তু ইউজার পুরনো অবস্থা দেখছেন? সার্ভার-সাইড ক্যাশ (যেমন Redis-এ ইউজারের পারমিশন), CDN ক্যাশ বা অ্যাপের লোকাল স্টেট
- টেস্ট: লগআউট করে আবার লগইন, বা অন্য ডিভাইসে দেখা

### সম্পূর্ণ Decision Flow এক নজরে

```text
পেমেন্ট সফল কিন্তু অ্যাক্সেস নেই
│
├─ Dashboard-এ পেমেন্ট Succeeded?
│   ├─ না  → পেমেন্ট সমস্যা (3DS, pending, failed) → কাস্টমারকে জানান
│   └─ হ্যাঁ
│       ├─ প্রয়োজনীয় ইভেন্ট তৈরি হয়েছে?
│       │   └─ না → ভুল ফ্লো/ভুল ইভেন্টের উপর নির্ভর → ডেভকে জানান
│       └─ হ্যাঁ → এন্ডপয়েন্টে delivery attempt আছে?
│           ├─ না  → সাবস্ক্রিপশন/URL/মোড/Disabled চেক
│           └─ হ্যাঁ → রেসপন্স কোড?
│               ├─ 400 → signature: whsec (CLI vs Dashboard, Test vs Live), raw body
│               ├─ 5xx / timeout → হ্যান্ডলার এরর বা ধীরগতি → লগ দেখুন
│               └─ 200 → DB-তে কোন ইউজার আপডেট হলো?
│                   ├─ ভুল/কেউ না → metadata / ইউজার ম্যাপিং বাগ
│                   └─ সঠিক → ক্যাশ / সেশন / UI স্টেট
```

> [!MISTAKE] রুট-কজ খুঁজতে গিয়ে সাধারণ ভুল
> - Dashboard না দেখেই "Stripe-এর সমস্যা" বলে দেওয়া
> - শুধু অ্যাপ লগ দেখা, delivery attempts-এর রেসপন্স কোড না দেখা
> - সিগনেচার এরর ঠিক করার পর ব্যর্থ ইভেন্টগুলো Resend না করা, ফলে পুরনো কাস্টমাররা আটকে থাকেন
> - অজানা ইভেন্টে 400 বা 500 দেওয়া, ফলে অকারণে রিট্রাই জমে
> - টেস্ট শেষে ইচ্ছা করে বসানো `res.status(500)` বা `setTimeout` কোডে রেখে দেওয়া
> - বাগ রিপোর্টে event id, PaymentIntent id আর রেসপন্স কোড না দেওয়া

> [!LIVE]
> Live Mode-এ কাস্টমারের সমস্যা তদন্ত করার সময় শুধু দেখুন, Resend ছাড়া কিছু বদলাবেন না। Live ইভেন্ট Resend বা রিফান্ড করার আগে টিম লিড বা ফাইন্যান্সের অনুমতি নিন। কাস্টমারের কার্ড বা ব্যক্তিগত তথ্য বাগ রিপোর্টে কপি করবেন না।

## সারসংক্ষেপ

- Webhook ইভেন্ট ডুপ্লিকেট, উল্টো ক্রমে ও দেরিতে আসতে পারে: অ্যাপকে এসব সামলাতে হবে
- 2xx ছাড়া সব রেসপন্সে Stripe রিট্রাই করে; Live Mode-এ এক্সপোনেনশিয়াল ব্যাকঅফে ৩ দিন পর্যন্ত, Test Mode-এ ভিন্ন হতে পারে
- ভুল সিগনেচার ও পুরনো টাইমস্ট্যাম্পে 400, অজানা ইভেন্টে 200 ও ইগনোর
- দ্রুত 200 দিয়ে ভারী কাজ কিউতে: টাইমআউট ও ডুপ্লিকেট এড়ায়
- "পেমেন্ট সফল, অ্যাক্সেস নেই": Dashboard → Events → delivery attempts → লগ → সিক্রেট → সাবস্ক্রিপশন → হ্যান্ডলার → metadata → ক্যাশ

## বাড়ির কাজ
