> [!DANGER] শুধু নিজের ল্যাবে, কখনো আসল সাইটে নয়
> এই লেসনের প্রতিটি টেস্ট শুধু নিজের লোকাল অ্যাপ, নিজের Stripe Sandbox (Test Mode), অথবা OWASP Juice Shop, crAPI, VAmPI ও PortSwigger Web Security Academy-র মতো ইচ্ছা করে দুর্বল ল্যাবে করবেন। কোনো আসল দোকানে দাম বদলানো, কুপন অপব্যবহার বা অন্যের ইনভয়েস দেখার চেষ্টা প্রতারণা ও অনুমতিহীন অ্যাক্সেস, যা দণ্ডনীয় অপরাধ। Race Condition টেস্ট নিজের ল্যাবেও স্বাভাবিক, অল্প সংখ্যক রিকোয়েস্টে করুন।

স্ক্যানার টুল SQL Injection খুঁজে দিতে পারে, কিন্তু "কুপন দুইবার ব্যবহার করা যায়" এমন বাগ খুঁজে দিতে পারে না। কারণ এগুলো কোডের ভুল নয়, ব্যবসার নিয়মের ভুল। এদের বলে Business Logic Vulnerability (ব্যবসায়িক নিয়ম বাস্তবায়নের দুর্বলতা)।

পেমেন্ট সিস্টেমে এই বাগগুলো সরাসরি টাকার ক্ষতি করে। আর এখানেই একজন ম্যানুয়াল QA-এর সবচেয়ে বড় শক্তি: আপনি ব্যবসার নিয়ম জানেন।

## এই লেসনে যা শিখবেন

- দাম ও পরিমাণ বদল (Price/Amount Tampering) আর মুদ্রা বদল (Currency Manipulation)
- কুপন অপব্যবহার: বারবার ব্যবহার, একসাথে একাধিক, বড়-ছোট হাতের ভিন্নতা
- নেগেটিভ পরিমাণ ও নেগেটিভ quantity
- Race Condition আর Double Spending
- IDOR/BOLA: অন্যের অর্ডার বা ইনভয়েস দেখা
- প্রতিটির জন্য: কী, নিজের ল্যাবে কীভাবে টেস্ট, নিরাপদ আচরণ কেমন, আর ফিক্স কী

## প্রস্তুতি: আপনার ল্যাব

দুইটি ল্যাব কাজে লাগবে:

1. **OWASP Juice Shop** (`docker run --rm -p 3000:3000 bkimminich/juice-shop`): এর বাস্কেট আর চেকআউটে ইচ্ছা করে লজিক বাগ রাখা আছে
2. **নিজের ছোট চেকআউট API**: আগের লেসনের Express সার্ভারে একটি `/checkout` রুট, যা Stripe Test Mode-এ PaymentIntent বানায়

রিকোয়েস্ট বদলানোর জন্য Postman, curl, অথবা Burp Suite Community বা OWASP ZAP লাগবে। Proxy সেটআপ বিস্তারিত শিখবেন [Burp ও ZAP লেসনে](/lessons/burp-zap-intercept/)।

প্রতিটি টেস্টে দুইটি নিজের টেস্ট অ্যাকাউন্ট রাখুন: **অ্যাকাউন্ট A** আর **অ্যাকাউন্ট B**।

## ১. Price/Amount Tampering (দাম বদল)

### কী

ক্লায়েন্ট দাম বা মোট টাকা পাঠায়, আর সার্ভার সেটা বিশ্বাস করে। যেমন একটি কোর্স সাইটের দুর্বল কোড:

```js
// দুর্বল: ক্লায়েন্টের পাঠানো amount সরাসরি Stripe-এ
app.post('/checkout', async (req, res) => {
  const { courseId, amount } = req.body;
  const pi = await stripe.paymentIntents.create({ amount, currency: 'usd' });
  res.json({ clientSecret: pi.client_secret });
});
```

### নিজের ল্যাবে কীভাবে টেস্ট করবেন

1. স্বাভাবিকভাবে চেকআউট করুন, রিকোয়েস্ট ধরুন (DevTools বা Proxy)
2. Body-তে `price`, `amount`, `total`, `unit_price` জাতীয় ফিল্ড খুঁজুন
3. Postman-এ একই রিকোয়েস্ট বানিয়ে মান কমান, যেমন `150000` থেকে `100`
4. Stripe Dashboard (Test Mode) → Payments-এ দেখুন PaymentIntent কত টাকার হলো, আর অ্যাপে অর্ডার কত টাকার দেখাচ্ছে

```bash
curl -s -X POST http://localhost:4242/checkout \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <tester-A-token>" \
  -d '{"courseId":"qa-101","amount":100}'
```

### নিরাপদ আচরণ

ক্লায়েন্টের `amount` উপেক্ষা হবে বা 400 আসবে। PaymentIntent-এর amount সবসময় কোর্সের আসল দাম।

### ফিক্স

```js
// নিরাপদ: দাম সার্ভারের ডেটা থেকে
app.post('/checkout', async (req, res) => {
  const course = await db.courses.findById(req.body.courseId);
  if (!course) return res.status(404).json({ error: 'not_found' });
  const pi = await stripe.paymentIntents.create({
    amount: course.priceInCents,
    currency: course.currency,
    metadata: { courseId: course.id, userId: req.user.id },
  });
  res.json({ clientSecret: pi.client_secret });
});
```

আর Webhook-এ অর্ডার paid করার আগে মিলিয়ে নিন: `pi.amount === order.expectedAmount` এবং মুদ্রাও মিলছে কিনা। Stripe Checkout ব্যবহার করলে Dashboard-এ বানানো Price আইডি ব্যবহার করুন, ক্লায়েন্টের পাঠানো দাম নয়।

## ২. Currency Manipulation (মুদ্রা বদল)

### কী

দাম সার্ভার থেকে এলেও মুদ্রা যদি ক্লায়েন্ট থেকে আসে, তাহলে `1500` টাকা হয়ে যেতে পারে অন্য মুদ্রার `1500` একক, যার মূল্য অনেক কম। আবার কিছু মুদ্রায় দশমিক নেই (Zero-decimal currency, যেমন JPY), তাই একই সংখ্যার মানে বদলে যায়।

### টেস্ট

- রিকোয়েস্টে `currency` ফিল্ড থাকলে অন্য একটি সাপোর্টেড মুদ্রায় বদলান
- অ্যাপে কোর্সের দাম আর Stripe-এ PaymentIntent-এর amount ও currency মিলিয়ে দেখুন
- অসমর্থিত মুদ্রা কোড দিন (যেমন `xyz`), এরর কি পরিষ্কার?

### নিরাপদ আচরণ ও ফিক্স

মুদ্রা সার্ভারের দামের তালিকা থেকে নির্ধারিত হয়। বহু-মুদ্রার সাইটে প্রতিটি মুদ্রার জন্য আলাদা দাম সার্ভারে সংরক্ষিত থাকে। Webhook-এ amount আর currency দুইটিই মেলানো হয়।

## ৩. Coupon Abuse (কুপন অপব্যবহার)

### কী

ঈদ বা ১১.১১ সেলে কুপন সবচেয়ে বেশি অপব্যবহার হয়। কমন ধরন:

| ধরন | উদাহরণ |
| --- | --- |
| বারবার ব্যবহার | এককালীন `WELCOME50` একই অ্যাকাউন্টে বারবার |
| স্ট্যাকিং | `EID20` আর `WELCOME50` একসাথে দিয়ে ৭০% ছাড়, যেখানে নিয়ম "একটিই" |
| কেস ভিন্নতা | `welcome50`, `Welcome50`, ` WELCOME50 ` (স্পেসসহ) আলাদা কুপন হিসেবে গণ্য |
| মেয়াদোত্তীর্ণ | পুরনো কুপন API দিয়ে এখনো কাজ করে |
| শর্ত ফাঁকি | "৳১০০০-এর বেশি কেনায়" কুপন দিয়ে পরে পণ্য সরিয়ে ৳২০০ করা |
| অন্যের কুপন | নির্দিষ্ট ইউজারের রেফারেল কুপন অন্যজন ব্যবহার |

### টেস্ট

1. অ্যাকাউন্ট A দিয়ে এককালীন কুপন ব্যবহার করে অর্ডার সম্পন্ন করুন
2. আবার একই কুপন দিন: প্রত্যাশিত "ইতিমধ্যে ব্যবহৃত"
3. ছোট হাতে, স্পেসসহ, মিশ্র কেসে দিন
4. দুইটি কুপন একসাথে (রিকোয়েস্টে অ্যারে বা দুইবার `coupon` প্যারামিটার)
5. কুপন দেওয়ার পর কার্ট বদলান, তারপর চেকআউট: ছাড় কি আবার হিসাব হলো?

### ফিক্স

- কুপন কোড সংরক্ষণের আগে নরমালাইজ (trim, বড় হাতে)
- ব্যবহারের রেকর্ড টেবিলে `UNIQUE(coupon_id, user_id)` কনস্ট্রেইন্ট
- স্ট্যাকিং নিয়ম সার্ভারে; চূড়ান্ত দাম চেকআউটের মুহূর্তে আবার হিসাব
- মেয়াদ ও শর্ত সার্ভারে যাচাই

## ৪. Negative Amount / Negative Quantity

### কী

`quantity: -1` দিলে দাম নেগেটিভ হয়ে মোট কমে যায়, বা রিফান্ডে টাকা উল্টো দিকে যায়। একটি বাস্কেটে একটা দামি পণ্য `+1` আর একটা সস্তা পণ্য `-5` দিলে মোট প্রায় শূন্য হতে পারে।

OWASP Juice Shop-এ এর একটি পরিচিত চ্যালেঞ্জ আছে: বাস্কেটে নেগেটিভ পরিমাণ দিয়ে এমন অর্ডার করা যাতে দোকান উল্টো আপনাকে টাকা দেয়। আরেকটি চ্যালেঞ্জে নিজের বাস্কেটের বদলে অন্যের বাস্কেটে পণ্য যোগ করা যায়। Score Board-এ "Improper Input Validation" আর "Broken Access Control" ক্যাটাগরিতে এগুলো খুঁজুন।

### টেস্ট

- quantity: `0`, `-1`, `1.5`, `"abc"`, `999999999`, `null`
- amount বা refund_amount: `-100`, `0`, পেমেন্টের চেয়ে বেশি
- ফ্রন্টএন্ডে মাইনাস বাটন না থাকলেও API-তে সরাসরি পাঠান

### নিরাপদ আচরণ ও ফিক্স

সার্ভার স্কিমা ভ্যালিডেশন: quantity ১ থেকে যুক্তিসংগত সর্বোচ্চ পর্যন্ত পূর্ণসংখ্যা, নইলে 400। রিফান্ডের মোট পরিমাণ কখনো মূল পেমেন্ট ছাড়াবে না (Stripe নিজেও মূল চার্জের বেশি রিফান্ড দেয় না, কিন্তু আপনার অ্যাপের ওয়ালেট বা ক্রেডিট সিস্টেম আলাদা, সেটা আপনাকেই রক্ষা করতে হবে)। ইনপুট ভ্যালিডেশন বিস্তারিত আছে [ইনপুট ভ্যালিডেশন লেসনে](/lessons/input-validation-rate-limiting/)।

## ৫. Race Condition (সমান্তরাল রিকোয়েস্টের দৌড়)

### কী

Race Condition (দুই বা বেশি রিকোয়েস্ট একসাথে চললে ফলাফল ক্রমের উপর নির্ভর করে ভুল হওয়া)। সাধারণ কোড:

```text
১. কুপন কি ব্যবহৃত?  -> না
২. ছাড় দাও
৩. কুপন 'ব্যবহৃত' চিহ্ন দাও
```

ধাপ ১ আর ৩-এর মাঝে কয়েক মিলিসেকেন্ড ফাঁক থাকে। ২০টি রিকোয়েস্ট একসাথে এলে কয়েকটি ধাপ ১-এ "না" পেয়ে যায়। ফল: এককালীন কুপন কয়েকবার। একইভাবে একই অর্ডারে একসাথে দুইটি রিফান্ড রিকোয়েস্ট দুইবার রিফান্ড দিতে পারে।

উপমা: একটি bKash অ্যাকাউন্টে ৫০০ টাকা। দুইটি ফোন থেকে ঠিক একই মুহূর্তে ৫০০ করে পাঠানোর চেষ্টা। ঠিকমতো লক না থাকলে দুইটিই "ব্যালান্স আছে" দেখে পাস হয়ে যেত।

### নিজের ল্যাবে কীভাবে টেস্ট করবেন (ধারণাগত)

শুধু নিজের লোকাল অ্যাপে, অল্প কয়েকটি (যেমন ১০ থেকে ২০টি) রিকোয়েস্টে:

- **Burp Suite Repeater**: একই রিকোয়েস্টের কয়েকটি কপি একটি গ্রুপে রেখে "Send group in parallel" অপশন দিয়ে একসাথে পাঠানো যায়। নতুন Burp ভার্সনে এটা প্রায় একই মুহূর্তে রিকোয়েস্ট পৌঁছায়
- **Turbo Intruder**: Burp-এর একটি এক্সটেনশন, যা সমান্তরাল রিকোয়েস্টের জন্য বানানো। এটা শক্তিশালী, তাই শুধু নিজের ল্যাবে এবং কম সংখ্যায়
- তারপর DB বা Dashboard দেখুন: কুপন কতবার ব্যবহৃত হলো, রিফান্ড কয়টা হলো

PortSwigger Web Security Academy-তে "Race conditions" টপিকে বৈধভাবে এই কৌশল অনুশীলনের ল্যাব আছে।

### নিরাপদ আচরণ

২০টি সমান্তরাল রিকোয়েস্টে ঠিক একটি সফল, বাকিগুলো স্পষ্ট এরর (যেমন 409 Conflict)।

### ফিক্স

- অ্যাটমিক আপডেট: `UPDATE coupons SET used = true WHERE id = ? AND used = false` তারপর affected rows ১ কিনা দেখা
- ডাটাবেস লক (`SELECT ... FOR UPDATE`) বা ট্রানজ্যাকশন
- ইউনিক কনস্ট্রেইন্ট: `UNIQUE(order_id)` রিফান্ড টেবিলে, যদি এক অর্ডারে একটিই রিফান্ড নিয়ম হয়
- Stripe API কলে Idempotency-Key (একই কি দিয়ে বারবার পাঠালে Stripe একবারই কাজ করে); বিস্তারিত [Idempotency লেসনে](/lessons/idempotency-testing/)

## ৬. Double Spending (একই টাকা দুইবার খরচ)

### কী

একই ব্যালান্স, গিফট কার্ড, ক্রেডিট বা পেমেন্ট দিয়ে দুইবার কেনাকাটা। কারণ হতে পারে Race Condition, অথবা ডুপ্লিকেট Webhook ইভেন্ট দুইবার প্রসেস হওয়া, অথবা "Pay" বাটনে ডাবল ক্লিক।

উদাহরণ: একটি রাইড অ্যাপে ওয়ালেটে ২০০ টাকা। একসাথে দুইটি রাইডের পেমেন্ট ওয়ালেট থেকে, দুইটিই পাস।

### টেস্ট

- নিজের ল্যাবে ওয়ালেট বা গিফট কার্ড দিয়ে সমান্তরালে দুইটি অর্ডার
- "Pay" বাটনে দ্রুত দুইবার ক্লিক; Network ট্যাবে কয়টা রিকোয়েস্ট গেল দেখুন
- একই Webhook ইভেন্ট দুইবার পাঠান ([Webhook টেস্ট কেস লেসন](/lessons/webhook-test-cases/)): ব্যালান্স বা ক্রেডিট দুইবার যোগ হয় কিনা

### ফিক্স

ব্যালান্স কমানো অ্যাটমিক (`UPDATE wallets SET balance = balance - ? WHERE user_id = ? AND balance >= ?`), লেজার টেবিল, Webhook-এ event.id দিয়ে Idempotency, ফ্রন্টএন্ডে বাটন ডিসেবল (শুধু UX, সুরক্ষা নয়) আর ব্যাকএন্ডে Idempotency-Key।

## ৭. IDOR/BOLA (অন্যের অর্ডার বা ইনভয়েস)

### কী

IDOR (Insecure Direct Object Reference, সরাসরি আইডি দিয়ে অবজেক্ট অ্যাক্সেস কিন্তু মালিকানা যাচাই নেই)। API জগতে একে বলে BOLA। `GET /api/invoices/5012` থেকে `5013` করলেই অন্যের ইনভয়েস, যাতে নাম, ঠিকানা, ফোন, কেনাকাটা।

Juice Shop-এ অন্যের বাস্কেট দেখার একটি চ্যালেঞ্জ ঠিক এই ধরনের।

### টেস্ট

1. অ্যাকাউন্ট A আর B দুইটিতেই একটি করে অর্ডার করুন, আইডি নোট করুন
2. A-এর টোকেন দিয়ে B-এর অর্ডার, ইনভয়েস, রিসিপ্ট PDF, রিফান্ড রিকোয়েস্ট সব এন্ডপয়েন্টে চেষ্টা
3. শুধু GET নয়: PUT, PATCH, DELETE, আর `POST /api/orders/{id}/refund`
4. আইডি শুধু URL-এ নয়, Body, Query, Header-এও থাকতে পারে

### নিরাপদ আচরণ ও ফিক্স

B-এর অবজেক্টে A পাবে 404 (অস্তিত্বও প্রকাশ না করা ভালো) বা 403। ফিক্স: প্রতিটি কোয়েরিতে মালিকানা শর্ত:

```js
const invoice = await db.invoices.findOne({ id: req.params.id, userId: req.user.id });
if (!invoice) return res.status(404).json({ error: 'not_found' });
```

UUID-এর মতো অনুমান-কঠিন আইডি সহায়ক, কিন্তু Ownership Check-এর বিকল্প নয়।

> [!TIP] রিপোর্টে প্রভাব লিখুন
> লজিক বাগের রিপোর্টে শুধু "দাম বদলানো যায়" নয়, টাকার অঙ্কে প্রভাব লিখুন: "৳১৫০০-এর কোর্স ৳১-এ কেনা যায়; প্রতিটি বিক্রিতে ৳১৪৯৯ ক্ষতি।" এতে প্রায়োরিটি দ্রুত ঠিক হয়।

## হাতেকলমে অনুশীলন: টেস্ট কেস টেবিল

নিচের টেবিল নিজের ল্যাব অ্যাপ আর Juice Shop-এ চালান।

| ID | দুর্বলতা | টেস্ট (নিজের ল্যাবে) | প্রত্যাশিত নিরাপদ আচরণ | ফিক্স |
| --- | --- | --- | --- | --- |
| PL-01 | Price Tampering | চেকআউটে `amount` কমিয়ে পাঠানো | উপেক্ষা বা 400; PI-তে আসল দাম | সার্ভারে দাম লুকআপ |
| PL-02 | Amount mismatch | Webhook-এ PI amount আর অর্ডারের দাম ভিন্ন | অর্ডার paid হয় না, অ্যালার্ট | Webhook-এ amount+currency মেলানো |
| PL-03 | Currency | `currency` বদলে পাঠানো | 400 বা সার্ভারের মুদ্রা | মুদ্রা সার্ভারে নির্ধারিত |
| PL-04 | Coupon reuse | এককালীন কুপন দ্বিতীয়বার | "ব্যবহৃত" এরর | UNIQUE(coupon, user) |
| PL-05 | Coupon case | `welcome50`, ` WELCOME50 ` | একই কুপন হিসেবে গণ্য, পুনর্ব্যবহার নয় | নরমালাইজ |
| PL-06 | Coupon stacking | দুইটি কুপন একসাথে | শুধু নিয়মমতো একটি | সার্ভারে স্ট্যাকিং নিয়ম |
| PL-07 | Negative qty | `quantity: -1` | 400 | স্কিমা ভ্যালিডেশন |
| PL-08 | Over-refund | পেমেন্টের চেয়ে বেশি রিফান্ড | 400 | মোট রিফান্ড ≤ মূল পেমেন্ট |
| PL-09 | Race: coupon | ১০টি সমান্তরাল রিকোয়েস্ট একই কুপনে | ঠিক ১টি সফল | অ্যাটমিক আপডেট/লক |
| PL-10 | Race: refund | একই অর্ডারে ২টি রিফান্ড একসাথে | ১টি সফল, অন্যটি 409 | লক + Idempotency-Key |
| PL-11 | Double spend | ওয়ালেট দিয়ে সমান্তরালে ২টি অর্ডার | ব্যালান্স কখনো নেগেটিভ নয় | শর্তসহ অ্যাটমিক ডেবিট |
| PL-12 | IDOR | A-এর টোকেনে B-এর ইনভয়েস | 404/403 | Ownership check |

> [!MISTAKE] সাধারণ ভুল
> - শুধু UI দিয়ে টেস্ট করে "মাইনাস দেওয়া যায় না" লেখা; API সরাসরি টেস্ট না করা
> - একটি অ্যাকাউন্ট দিয়ে IDOR টেস্ট: নিজের অবজেক্ট দেখে "কাজ করছে" ভাবা
> - Race টেস্টে শত শত রিকোয়েস্ট পাঠানো; এটা লোড টেস্ট হয়ে যায় এবং শেয়ার করা ল্যাব বা Stripe Sandbox-এর রেট লিমিটে আঘাত করে
> - Stripe Dashboard-এ PaymentIntent-এর amount না মিলিয়ে শুধু অ্যাপের স্ক্রিন দেখা
> - ফিক্স হিসেবে শুধু "ফ্রন্টএন্ডে ভ্যালিডেশন যোগ করুন" লেখা

> [!CHECK] লেসন শেষে
> - PL-01 থেকে PL-12 নিজের ল্যাবে চালিয়ে Actual লেখা হয়েছে
> - Juice Shop-এ নেগেটিভ পরিমাণ আর অন্যের বাস্কেট সংক্রান্ত অন্তত একটি চ্যালেঞ্জ চেষ্টা করেছেন
> - প্রতিটি বাগের জন্য সার্ভার-সাইড ফিক্স বলতে পারেন

## সারসংক্ষেপ

- বিজনেস লজিক বাগ স্ক্যানার খুঁজে পায় না; ব্যবসার নিয়ম জানা QA-ই সবচেয়ে ভালো খোঁজেন
- দাম ও মুদ্রা সার্ভার থেকে, Stripe amount সার্ভার থেকে, Webhook-এ amount+currency মেলানো
- কুপন: নরমালাইজ, ইউনিক কনস্ট্রেইন্ট, স্ট্যাকিং ও মেয়াদ সার্ভারে

- Race Condition ও Double Spending: অ্যাটমিক আপডেট, লক, ইউনিক কনস্ট্রেইন্ট, Idempotency
