> [!DANGER] শুধু ল্যাব ও নিজের অ্যাপে
> SQL Injection ও XSS পেলোড শুধু ইচ্ছাকৃতভাবে দুর্বল ল্যাবে (OWASP Juice Shop, DVWA, PortSwigger Web Security Academy) বা নিজের লোকাল অ্যাপে চালাবেন। কোনো আসল সাইটের ফর্মে "শুধু একটা quote" দেওয়াও অনুমতিহীন টেস্ট। Card testing ও brute force এখানে শুধু ধারণা, শনাক্ত করা ও প্রতিরোধ হিসেবে শেখানো হচ্ছে; এর জন্য কোনো স্ক্রিপ্ট লিখবেন না, চালাবেন না। আগে পড়ুন: [নৈতিকতা ও দায়িত্বশীল প্রকাশ](/lessons/ethics-responsible-disclosure/)।

চেকআউট পেজে ইউজার নাম, ঠিকানা, ফোন, কুপন কোড, পরিমাণ লেখে। প্রতিটি ঘর আসলে সার্ভারের দিকে খোলা একটা জানালা। Input Validation (ইনপুট গ্রহণের আগে যাচাই করা যে সেটা প্রত্যাশিত ধরনের) এই জানালায় গ্রিল লাগায়।

আর Rate Limiting (নির্দিষ্ট সময়ে কতবার রিকোয়েস্ট করা যাবে তার সীমা) ঠিক করে, কেউ একই জানালায় হাজারবার ধাক্কা দিতে পারবে না। এই লেসনে দুটোই হাতেকলমে দেখব।

## এই লেসনে যা শিখবেন

- চেকআউট ও বিলিং ফর্মের প্রতিটি ফিল্ডে কী যাচাই করবেন
- ক্লায়েন্ট-সাইড বনাম সার্ভার-সাইড ভ্যালিডেশন
- SQL Injection-এর ধারণা, ল্যাবে নিরাপদ পেলোড এবং সমাধান
- XSS (Reflected ও Stored), ল্যাবে নিরীহ প্রমাণ এবং সমাধান
- Card testing আক্রমণের ধারণা, শনাক্তকরণ ও প্রতিরোধ
- নিজের অ্যাপে Rate Limit আছে কি না যাচাই (429)

## চেকআউট ফর্মের ফিল্ড ধরে ভ্যালিডেশন

একটা Daraz-এর মতো দোকানের চেকআউট ধরুন। প্রতিটি ফিল্ডে টেস্টার কী দেখবে:

| ফিল্ড | বৈধ উদাহরণ | যা চেষ্টা করবেন | প্রত্যাশিত আচরণ |
|---|---|---|---|
| নাম | `রহিম উদ্দিন`, `Rahim Uddin` | খালি, শুধু স্পেস, ৫০০ অক্ষর, ইমোজি | খালি/অতি লম্বা বাতিল; বাংলা নাম গ্রহণ |
| ঠিকানা | `বাড়ি ১২, রোড ৫, মিরপুর` | ২০০০ অক্ষর, HTML ট্যাগ | দৈর্ঘ্যের সীমা; ট্যাগ লেখা হিসেবে দেখাবে, চলবে না |
| ইমেইল | `user@example.com` | `user@`, `@example.com`, স্পেস | ফরম্যাট ভুল হলে স্পষ্ট বার্তা |
| ফোন | `01712345678` | `+8801712345678`, `0171`, অক্ষর | বাংলাদেশি ফরম্যাট গ্রহণ, ভুল দৈর্ঘ্য বাতিল |
| পরিমাণ (quantity) | `1`, `3` | `0`, `-1`, `1.5`, `99999`, `"abc"` | শুধু ১ থেকে সীমা পর্যন্ত পূর্ণসংখ্যা |
| অঙ্ক (amount) | সার্ভার হিসাব করবে | ক্লায়েন্ট থেকে `amount: 1` পাঠানো | সার্ভার নিজের দাম ব্যবহার করবে |
| কুপন | `EID2026` | ছোট হাতের, স্পেসসহ, মেয়াদোত্তীর্ণ, ২০০ অক্ষর, quote | নিয়মমতো বাতিল, কোনো error leak নয় |

> [!TIP] দাম কখনো ক্লায়েন্ট থেকে নয়
> PaymentIntent-এর `amount` সার্ভারে কার্টের আইটেম ও ডাটাবেসের দাম থেকে হিসাব হওয়া উচিত। ব্রাউজার থেকে আসা দাম বিশ্বাস করলে যে কেউ ৫০০০ টাকার কোর্স ১ টাকায় কিনবে। বিস্তারিত: [পেমেন্ট লজিক দুর্বলতা](/lessons/payment-logic-vulnerabilities/)।

### ক্লায়েন্ট-সাইড বনাম সার্ভার-সাইড

- **ক্লায়েন্ট-সাইড** (ব্রাউজারে, যেমন HTML `required`, `min`, JS চেক): ইউজারকে দ্রুত সাহায্য করে। কিন্তু DevTools, Postman বা Burp দিয়ে সহজেই এড়ানো যায়।
- **সার্ভার-সাইড** (API-তে): এটাই আসল সুরক্ষা। প্রতিটি নিয়ম এখানে আবার যাচাই হতে হবে।

টেস্টারের কাজ: প্রতিটি ফিল্ড UI দিয়ে একবার, আর সরাসরি API দিয়ে একবার পরীক্ষা করা। Postman দিয়ে এভাবে:

```http
POST /api/cart/items HTTP/1.1
Host: localhost:3000
Content-Type: application/json

{ "productId": 7, "quantity": -5 }
```

প্রত্যাশা: `400 Bad Request` ও স্পষ্ট বার্তা, যেমন `"quantity must be between 1 and 10"`। `201 Created` এলে বাগ।

## SQL Injection: ধারণা, ল্যাবে নিরাপদ টেস্ট ও সমাধান

SQL Injection (ইউজারের ইনপুট SQL কোয়েরির অংশ হয়ে গিয়ে কোয়েরির অর্থ বদলে দেয়) ঘটে যখন কোড এভাবে লেখা:

```js
// দুর্বল কোড: কখনো এভাবে লিখবেন না
const sql = "SELECT * FROM coupons WHERE code = '" + req.body.code + "'";
```

ইউজার যদি কোডের জায়গায় এমন কিছু লেখে যাতে quote আছে, কোয়েরির গঠনই বদলে যায়। এটা এমন, যেন দোকানদারকে লিখিত অর্ডার দিলেন আর অর্ডারের ভেতরেই লিখলেন "আর ক্যাশবাক্সও দিয়ে দিন", দোকানদার সেটাও পড়ে মেনে নিল।

### ল্যাবে নিরাপদ পেলোড

শুধু DVWA (Security level: low) বা লোকালে চলা Juice Shop-এ:

```text
'
```

```text
' OR '1'='1
```

- প্রথমটি, একটা single quote: কোয়েরি ভেঙে গেলে ডাটাবেস error বা অস্বাভাবিক আচরণ দেখা যায়। এটা দুর্বলতার প্রথম লক্ষণ।
- দ্বিতীয়টি: শর্তটা সবসময় সত্য করে দেয়, ফলে DVWA-র User ID ফিল্ডে সব ইউজারের তালিকা চলে আসে।

এর বেশি কিছু (ডাটা বের করা, টেবিল মোছা) আমরা করব না। টেস্টারের কাজ দুর্বলতা প্রমাণ করা ও রিপোর্ট করা, ক্ষতি করা নয়।

### সমাধান: Parameterized Query

```js
// নিরাপদ: ইনপুট ডেটা হিসেবে যায়, কোড হিসেবে নয়
const [rows] = await db.execute('SELECT * FROM coupons WHERE code = ?', [req.body.code]);
```

ORM (যেমন Prisma, Sequelize) সাধারণত এটা নিজেই করে, যদি না কেউ raw query-তে স্ট্রিং জোড়া লাগায়। টেস্টার হিসেবে রিপোর্টে সমাধান হিসেবে "parameterized query / prepared statement" লিখুন।

## XSS: ধারণা, ল্যাবে নিরীহ প্রমাণ ও সমাধান

XSS বা Cross-Site Scripting (আক্রমণকারীর লেখা জাভাস্ক্রিপ্ট অন্য ইউজারের ব্রাউজারে চলে যায়) দুই রকম:

- **Reflected XSS**: ইনপুট সাথে সাথে পেজে ফিরে আসে, যেমন সার্চ পেজে "আপনি খুঁজেছেন: ..."। লিংকে পেলোড বসিয়ে কাউকে পাঠালে তার ব্রাউজারে চলে।
- **Stored XSS**: ইনপুট ডাটাবেসে জমা থাকে, যেমন প্রোডাক্ট রিভিউ বা ডেলিভারি ঠিকানা। পরে যে-ই দেখবে, এমনকি অ্যাডমিন, তার ব্রাউজারে চলবে।

পেমেন্ট সাইটে Stored XSS বিশেষ বিপজ্জনক: অ্যাডমিন অর্ডার প্যানেলে ঠিকানা খুললেই স্ক্রিপ্ট চলে, অথবা চেকআউট পেজে স্ক্রিপ্ট ঢুকে কার্ডের তথ্য চুরি করতে পারে।

### ল্যাবে নিরীহ পেলোড

শুধু Juice Shop বা PortSwigger Academy-র ল্যাবে। ক্লাসিক পেলোড হলো script ট্যাগের ভেতরে `alert(1)`। ট্যাগ ছাড়া এমন বিকল্পও প্রচলিত:

```text
<img src=x onerror=alert(1)>
```

```text
<svg onload=alert(1)>
```

পপআপে `1` দেখা মানেই প্রমাণ, স্ক্রিপ্ট চলছে। কুকি চুরি বা অন্য কিছু করার দরকার নেই। Juice Shop-এর সার্চ বক্স Reflected XSS শেখার জন্য বানানো, আর PortSwigger-এর ফ্রি ল্যাবগুলো ধাপে ধাপে শেখায়: [portswigger.net/web-security/cross-site-scripting](https://portswigger.net/web-security/cross-site-scripting)।

> [!NOTE]
> পেলোড সবসময় কোড ব্লকে বা টুলে লিখুন। বাগ রিপোর্টের HTML ফিল্ডে বা উইকিতে কাঁচা পেস্ট করলে সেখানেই চলে যেতে পারে।

### সমাধান: Output Encoding ও CSP

- **Output encoding**: ইউজারের ডেটা HTML-এ বসানোর সময় `<` হয়ে যায় `&lt;`। React, Astro, Vue ডিফল্টভাবে এটা করে; বিপদ তখন, যখন কেউ `dangerouslySetInnerHTML`, `innerHTML` বা `v-html` ব্যবহার করে।
- **Content-Security-Policy (CSP)**: ব্রাউজারকে বলে কোন উৎসের স্ক্রিপ্ট চলবে। inline স্ক্রিপ্ট নিষিদ্ধ করলে XSS ঢুকলেও চলতে পারে না। বিস্তারিত: [PCI DSS বেসিক](/lessons/pci-dss-basics/)-এর Security Header অংশ।
- **ইনপুট ভ্যালিডেশন** সাহায্য করে, কিন্তু একা যথেষ্ট নয়।

## Rate Limiting ও Brute Force: Card Testing বুঝুন

### Card testing কী (শুধু ধারণা)

জালিয়াতরা কোথাও থেকে চুরি হওয়া কার্ড নম্বরের বিশাল তালিকা কেনে। কোনগুলো এখনো সচল, জানতে তারা ছোট কোনো সাইটে, যেমন ডোনেশন পেজ বা সস্তা কোর্স সাইটে, ছোট অঙ্কের পেমেন্ট চেষ্টা করে। সফল হলে কার্ডটা "চালু" বলে চিহ্নিত হয়, পরে বড় কেনাকাটায় ব্যবহার হয়।

মার্চেন্টের ক্ষতি:

- প্রতিটি চেষ্টায় ফি ও পরে dispute বা chargeback
- কার্ড নেটওয়ার্ক ও Stripe-এর কাছে অ্যাকাউন্টের সুনাম নষ্ট
- আসল গ্রাহকদের পেমেন্টও সন্দেহের তালিকায় পড়া

একই ধারণা লগইন বা OTP-তে brute force (অনেকবার আন্দাজ করে চেষ্টা)। আমরা এর কোনো স্ক্রিপ্ট লিখব না, শুধু চিনব ও ঠেকাব।

### শনাক্ত করার লক্ষণ

- অল্প সময়ে অনেক পেমেন্ট চেষ্টা, বেশিরভাগ declined
- একই IP, ডিভাইস বা অ্যাকাউন্ট থেকে অনেক আলাদা কার্ড
- খুব ছোট অঙ্ক, অস্বাভাবিক সময় (রাত ৩টা)
- একই কার্ডের ভিন্ন ভিন্ন মেয়াদ বা CVC দিয়ে বারবার চেষ্টা

### প্রতিরোধ

| স্তর | কী করে |
|---|---|
| IP-ভিত্তিক rate limit | একটা IP থেকে মিনিটে কতবার চেকআউট বা পেমেন্ট চেষ্টা |
| অ্যাকাউন্ট-ভিত্তিক সীমা | একটা অ্যাকাউন্টে ঘণ্টায় কতটা ব্যর্থ পেমেন্ট |
| কার্ড fingerprint সীমা | Stripe PaymentMethod-এর `card.fingerprint` দিয়ে একই কার্ডের বারবার চেষ্টা গোনা |
| CAPTCHA | সন্দেহজনক আচরণে মানুষ কি না যাচাই |
| Stripe Radar | মেশিন লার্নিং দিয়ে ঝুঁকি স্কোর; Radar for Fraud Teams থাকলে কাস্টম rule (যেমন একই IP থেকে বেশি কার্ড হলে block) |
| মনিটরিং | decline rate হঠাৎ বাড়লে অ্যালার্ট |
| লগইন বাধ্যতামূলক | অতিথি চেকআউটে ঝুঁকি বেশি হলে |

Stripe-এর ডকুমেন্টেশনে card testing নিয়ে আলাদা গাইড আছে: [docs.stripe.com](https://docs.stripe.com) খুলে "card testing" সার্চ করুন।

### টেস্টার কীভাবে Rate Limit যাচাই করবেন

শুধু নিজের লোকাল বা স্টেজিং অ্যাপে, অল্প কয়েকটা রিকোয়েস্টে:

```bash
for i in $(seq 1 15); do
  curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost:3000/api/coupon/apply \
    -H "Content-Type: application/json" -d '{"code":"WRONG'$i'"}'
done
```

প্রত্যাশা: প্রথম কয়েকটা `400` (ভুল কুপন), তারপর সীমা পেরোলে `429 Too Many Requests`। রেসপন্সে `Retry-After` হেডার থাকা ভালো অনুশীলন:

```bash
curl -i -X POST http://localhost:3000/api/coupon/apply -H "Content-Type: application/json" -d '{"code":"X"}'
```

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 60
Content-Type: application/json

{"error":"Too many attempts. Try again later."}
```

> [!LIVE] Stripe-এ চাপ দেবেন না
> এই লুপ কখনো সরাসরি Stripe API, প্রোডাকশন বা অন্যের সাইটে চালাবেন না। Stripe নিজেই API rate limit প্রয়োগ করে (সীমা পেরোলে 429), আর টেস্ট মোডের সীমা লাইভের চেয়ে কম। Stripe-এর উপর লোড টেস্ট করা তাদের নিয়মবিরুদ্ধ। লোড টেস্ট নিয়ে পরে: [k6 লোড টেস্টিং](/lessons/k6-load-testing/)।

| IV-04 | ইমেইল | `user@` | 400, স্পষ্ট বার্তা | Low |
| IV-05 | ফোন | `0171` | 400 | Low |
| IV-06 | নাম | বাংলা নাম | গ্রহণ ও সঠিক প্রদর্শন | Medium |

## হাতেকলমে অনুশীলন

1. Docker দিয়ে Juice Shop চালান: `docker run --rm -p 3000:3000 bkimminich/juice-shop`। ব্রাউজারে `http://localhost:3000` খুলুন।
2. সার্চ বক্সে `<img src=x onerror=alert(1)>` লিখে Enter দিন। পপআপ আসে কি না দেখুন। URL-এ পেলোডটা কোথায় বসেছে লক্ষ করুন।
3. Juice Shop-এর লগইনে ইমেইল ঘরে single quote দিয়ে দেখুন কী error আসে (এটা Juice Shop-এর একটা পরিচিত চ্যালেঞ্জ)।
4. DVWA থাকলে (Docker-এ চালানো যায়) Security level low করে SQL Injection পেজে `' OR '1'='1` দিন।
5. নিজের কোনো ছোট Express অ্যাপে `express-rate-limit` প্যাকেজ যোগ করে একটা endpoint-এ সীমা দিন, তারপর উপরের curl লুপ দিয়ে 429 যাচাই করুন।
6. প্রতিটি ফাইন্ডিং-এর জন্য [বাগ রিপোর্ট](/lessons/payment-bug-reports/) লিখুন: ধাপ, পেলোড (কোড ব্লকে), প্রত্যাশিত বনাম প্রকৃত ফল, সমাধানের প্রস্তাব।

> [!MISTAKE] সাধারণ ভুল
> - শুধু UI দিয়ে ভ্যালিডেশন টেস্ট করে "পাস" দেওয়া; API সরাসরি না দেখা।
> - বাংলা নাম বা `+880` ফোন বাতিল হওয়াকে স্বাভাবিক ধরে নেওয়া। এটাও বাগ, ব্যবহারযোগ্যতার।
> - XSS বা SQLi পেলোড আসল সাইটে "শুধু দেখার জন্য" দেওয়া।
> - Rate limit যাচাইয়ের নামে প্রোডাকশনে বা Stripe-এ হাজার রিকোয়েস্ট পাঠানো।
> - সমাধান হিসেবে "এই অক্ষরগুলো ব্লক করুন" লেখা; আসল সমাধান parameterized query ও output encoding।

## সারসংক্ষেপ

- ক্লায়েন্ট-সাইড ভ্যালিডেশন সুবিধা, সার্ভার-সাইড ভ্যালিডেশন সুরক্ষা; দুটোই টেস্ট করুন।
- দাম ও অঙ্ক সবসময় সার্ভারে হিসাব; quantity, ফোন, ইমেইলের সীমা সার্ভারে।
- SQL Injection-এর সমাধান parameterized query; XSS-এর সমাধান output encoding ও CSP।
- পেলোড শুধু ল্যাবে, সবসময় কোড ব্লকে।
- Card testing: অনেক কার্ড, ছোট অঙ্ক, বেশি decline; প্রতিরোধ rate limit, fingerprint, CAPTCHA, Radar, মনিটরিং।
- Rate limit যাচাই: নিজের এনভায়রনমেন্টে অল্প কয়েকটা রিকোয়েস্ট, প্রত্যাশা 429।
