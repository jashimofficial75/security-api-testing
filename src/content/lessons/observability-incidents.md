প্রোডাকশনে পেমেন্ট ভাঙলে প্রতি মিনিটে টাকা আর গ্রাহকের আস্থা দুটোই হারায়। তখন প্রশ্ন একটাই: কত দ্রুত বুঝতে পারব কী হয়েছে?

এর উত্তর **Observability** (লগ, মেট্রিক ও অ্যালার্ট দেখে সিস্টেমের ভেতরে কী ঘটছে তা বোঝার সক্ষমতা)। এই লেসনে শিখব একজন পেমেন্ট QA কীভাবে এটা টেস্ট করে, আর ইনসিডেন্টের সময় কী ভূমিকা রাখে।

## এই লেসনে যা শিখবেন

- Structured log আর correlation id দিয়ে একটা অর্ডারের পুরো গল্প খুঁজে পাওয়া
- লগে কী কখনো রাখা যাবে না
- পেমেন্টের মূল মেট্রিক: success rate, decline rate, webhook failure rate, latency p95
- অ্যালার্ট ও ফ্রি ড্যাশবোর্ড (Grafana, Stripe Dashboard-এর Workbench/লগ)
- অ্যালার্ট সত্যিই কাজ করে কিনা staging-এ টেস্ট করা
- প্রোডাকশন ইনসিডেন্টে QA: triage, রিপ্রোডিউস, টাইমলাইন, post-mortem, রিগ্রেশন টেস্ট
- একটা বাস্তবসম্মত ইনসিডেন্ট: webhook secret রোটেট, অ্যাপ আপডেট হয়নি

## লগ: correlation id-ই চাবি

### Structured log কী

সাধারণ লগ: `Payment failed for user`। এটা পড়ে কিছুই বোঝা যায় না।

**Structured log** (প্রতিটা লগ লাইন নির্দিষ্ট ফিল্ডসহ JSON আকারে) দেখতে এমন:

```json
{
  "time": "2026-11-01T08:15:42.120Z",
  "level": "error",
  "msg": "webhook signature verification failed",
  "service": "payments-api",
  "order_id": "ord_1001",
  "payment_intent": "pi_XXXXXXXXXXXX01",
  "event_id": "evt_XXXXXXXXXXXX01",
  "event_type": "payment_intent.succeeded",
  "stripe_request_id": "req_XXXXXXXXXXXX",
  "http_status": 400
}
```

এখন `order_id = ord_1001` দিয়ে সার্চ করলে চেকআউট থেকে webhook পর্যন্ত সব লাইন এক জায়গায় আসে।

### পেমেন্টে দরকারি correlation id

| id | কোথা থেকে | কাজে লাগে |
|---|---|---|
| `order_id` | আপনার অ্যাপ | গ্রাহক সাপোর্ট টিকিট থেকে খোঁজা |
| `payment_intent` (`pi_...`) | Stripe API উত্তর | Stripe Dashboard-এ সেই পেমেন্ট খোলা |
| `event_id` (`evt_...`) | webhook বডি | কোন ইভেন্ট এসেছিল, Dashboard থেকে resend |
| Stripe `Request-Id` (`req_...`) | Stripe API রেসপন্সের হেডার | Stripe-এর লগে সেই কল খোঁজা, Stripe সাপোর্টকে দেওয়া |
| নিজের `request_id` / trace id | আপনার সার্ভার/গেটওয়ে | এক রিকোয়েস্টের সব সার্ভিসের লগ জোড়া |
| `tran_id`, `val_id`, `paymentID`, `trxID` | SSLCommerz/bKash | লোকাল গেটওয়ের লেনদেন খোঁজা ([/lessons/bangladesh-gateways-sandbox/](/lessons/bangladesh-gateways-sandbox/)) |

Stripe প্রতিটা API রেসপন্সে একটা `Request-Id` হেডার পাঠায়। এটা লগ করে রাখলে Stripe Dashboard-এর লগে ঠিক সেই রিকোয়েস্ট খুঁজে পাওয়া যায়। বিস্তারিত: [Stripe docs](https://docs.stripe.com) এ "request IDs" লিখে খুঁজুন।

> [!DANGER] লগে কখনো নয়
> কার্ড নম্বর, CVC, মেয়াদ, `sk_test_`/`sk_live_` key, `whsec_` secret, Authorization হেডার, পাসওয়ার্ড, OTP, PIN, পুরো `client_secret`। লগ অনেক মানুষ ও টুল পড়ে, তাই এগুলো লগে যাওয়া মানেই ফাঁস। ইমেইল ও ফোন নম্বরও যতটা সম্ভব mask করুন (যেমন `01X******89`)। বিস্তারিত: [/lessons/sensitive-data-exposure/](/lessons/sensitive-data-exposure/) ও [/lessons/pci-dss-basics/](/lessons/pci-dss-basics/)।

QA হিসেবে লগ টেস্ট করুন: Test Mode-এ একটা পেমেন্ট করে লগ ফাইল বা লগ টুলে `4242` বা `sk_test` সার্চ করুন। কিছু পেলে সেটা বাগ।

## মেট্রিক, অ্যালার্ট ও ড্যাশবোর্ড

লগ বলে "এই একটা অর্ডারে কী হলো"। **মেট্রিক** (সময়ের সাথে মাপা সংখ্যা) বলে "সামগ্রিকভাবে সিস্টেম কেমন আছে"।

### পেমেন্টের মূল মেট্রিক

| মেট্রিক | হিসাব | কেন জরুরি |
|---|---|---|
| Payment success rate | সফল / মোট চেষ্টা | হঠাৎ কমলে কিছু ভেঙেছে |
| Decline rate | ব্যাংক প্রত্যাখ্যান / মোট | হঠাৎ বাড়লে কনফিগ সমস্যা বা card testing আক্রমণ ([/lessons/input-validation-rate-limiting/](/lessons/input-validation-rate-limiting/)) |
| Webhook failure rate | non-2xx webhook উত্তর / মোট | ৪০০/৫০০ বাড়লে অর্ডার আটকে যাচ্ছে |
| Webhook lag | ইভেন্ট তৈরি থেকে প্রসেস শেষ পর্যন্ত সময় | কিউ পিছিয়ে যাচ্ছে কিনা |
| Checkout latency p95 | ৯৫% চেকআউট রিকোয়েস্টের সময় | ধীর হলে ডাবল ক্লিক বাড়ে ([/lessons/k6-load-testing/](/lessons/k6-load-testing/)) |
| Pending orders > ৩০ মিনিট | সংখ্যা | webhook হারানো বা প্রসেসিং বাগ |

### অ্যালার্ট

**অ্যালার্ট** মানে একটা নিয়ম: "যদি গত ১০ মিনিটে webhook failure rate ৫%-এর বেশি হয়, অন-কল ইঞ্জিনিয়ারকে জানাও।" ভালো অ্যালার্টের বৈশিষ্ট্য:

- ইউজারের ক্ষতির সাথে সম্পর্কিত (success rate কমা), শুধু CPU বাড়া নয়
- খুব বেশি নয়, নাহলে মানুষ উপেক্ষা করতে শেখে ("alert fatigue")
- অ্যালার্ট মেসেজে কী দেখতে হবে তার লিংক (ড্যাশবোর্ড, runbook)

### ফ্রি টুল

- **Grafana** (ওপেন সোর্স): মেট্রিক ও লগ থেকে ড্যাশবোর্ড ও অ্যালার্ট। Prometheus, Loki ইত্যাদির সাথে চলে। [grafana.com](https://grafana.com)
- **Stripe Dashboard**: প্রতিটা API রিকোয়েস্টের লগ, ইভেন্ট আর webhook ডেলিভারির ইতিহাস (কোন endpoint কী status দিয়েছে, কবে আবার চেষ্টা হবে)। Stripe এখন এগুলো **Workbench** নামের ডেভেলপার প্যানেলে দেখায়; ইন্টারফেসের নাম সময়ের সাথে বদলাতে পারে।
- নিজের অ্যাপে: সহজ শুরুতে একটা `/health` endpoint আর কয়েকটা কাউন্টার যথেষ্ট।

> [!TIP] Stripe-এর webhook ডেলিভারি পেজ আপনার বন্ধু
> Webhook endpoint-এর ডেলিভারি তালিকায় প্রতিটা চেষ্টার status code আর আপনার সার্ভারের উত্তর দেখা যায়। হঠাৎ সব লাল (৪০০) হয়ে গেলে প্রায়ই সমস্যা signature যাচাইয়ে। এখান থেকে একটা ইভেন্ট resend-ও করা যায় ([/lessons/stripe-cli-webhooks/](/lessons/stripe-cli-webhooks/))।

### অ্যালার্ট সত্যিই কাজ করে কিনা টেস্ট করা

অ্যালার্ট লেখা হয়, কিন্তু অনেক সময় কেউ টেস্ট করে না। ফলে ভুল মেট্রিক নাম বা ভুল থ্রেশহোল্ডে সেটা কখনো ফায়ার হয় না। staging-এ (কখনো প্রোডাকশনে নয়) এভাবে টেস্ট করুন:

1. **Decline rate অ্যালার্ট**: Stripe-এর decline টেস্ট কার্ড (যেমন `4000 0000 0000 0002`) দিয়ে অল্প সময়ে অনেকগুলো ব্যর্থ পেমেন্ট করুন ([/lessons/stripe-test-cards/](/lessons/stripe-test-cards/))।
2. **Webhook failure অ্যালার্ট**: staging-এর webhook secret ইচ্ছা করে ভুল সেট করুন, তারপর `stripe trigger payment_intent.succeeded` চালান।
3. **Pending orders অ্যালার্ট**: webhook প্রসেসর বন্ধ রেখে কয়েকটা পেমেন্ট করুন।
4. প্রতিটায় দেখুন: অ্যালার্ট এলো কিনা, কত মিনিটে, মেসেজে কী লেখা, ঠিক চ্যানেলে গেল কিনা।
5. সব আবার স্বাভাবিক করুন এবং দেখুন অ্যালার্ট "resolved" হলো কিনা।

## প্রোডাকশন ইনসিডেন্টে QA-র ভূমিকা

**Incident** (ইনসিডেন্ট, এমন সমস্যা যা ইউজার বা ব্যবসাকে এখনই ক্ষতি করছে) হলে সাধারণত একজন incident lead থাকেন। QA-র কাজগুলো:

### ১. Triage: কতটা গুরুতর

- কতজন ইউজার প্রভাবিত? সব পেমেন্ট, নাকি শুধু একটা কার্ড ব্র্যান্ড বা একটা গেটওয়ে?
- কবে থেকে? কোন ডিপ্লয়ের পর?
- টাকা কাটা হচ্ছে কিন্তু অর্ডার হচ্ছে না, নাকি পেমেন্টই হচ্ছে না? (প্রথমটা বেশি গুরুতর, কারণ পরে রিফান্ড/সাপোর্ট লাগে)

### ২. Test Mode-এ রিপ্রোডিউস

কখনো প্রোডাকশনে আসল কার্ডে "চেষ্টা করে দেখা" নয়। একই কোড ভার্সন staging-এ বা লোকালে Test Mode-এ চালিয়ে একই ধাপ করুন। রিপ্রোডিউস হলে ডেভেলপারের ফিক্স যাচাই করা সহজ হয়।

> [!LIVE] প্রোডাকশনে সাবধান
> ইনসিডেন্টের চাপে Live Mode-এ টেস্ট পেমেন্ট, ম্যানুয়াল রিফান্ড বা ডাটাবেস এডিট করার লোভ হয়। এগুলো শুধু দায়িত্বপ্রাপ্ত ব্যক্তি, অনুমোদিত runbook মেনে করবেন। QA-র কাজ তথ্য দেওয়া, রিপ্রোডিউস করা আর ফিক্স যাচাই করা।

### ৩. টাইমলাইন রাখা

ইনসিডেন্ট চলাকালীন কেউ একজন সময় ধরে নোট রাখেন: কখন কী দেখা গেল, কে কী করল। QA প্রায়ই এই দায়িত্ব নেয়, কারণ টেস্টের মতোই এখানে সুনির্দিষ্টতা দরকার।

### ৪. Post-mortem ও রিগ্রেশন টেস্ট

সমস্যা মিটে গেলে **post-mortem** (ঘটনার বিশ্লেষণ) লেখা হয়। **Blameless** মানে ব্যক্তিকে দোষ নয়, সিস্টেম ও প্রক্রিয়ার ফাঁক খোঁজা: "কেন একজন মানুষের এক ভুলে পুরো পেমেন্ট বন্ধ হতে পারল?"

তারপর QA একটা **regression test** (পুরোনো বাগ আবার ফিরে এলে ধরবে এমন টেস্ট) লেখে, যাতে একই সমস্যা আর কখনো নীরবে প্রোডাকশনে না যায়।

## উদাহরণ: webhook secret রোটেট, অ্যাপ আপডেট হয়নি

একটা কোর্স-বিক্রির সাইটে ঘটনাটা এমন (কাল্পনিক, কিন্তু খুব বাস্তব):

- **১০:০০** নিরাপত্তার কারণে একজন ইঞ্জিনিয়ার Stripe Dashboard-এ webhook endpoint-এর signing secret রোল (roll) করলেন। পুরোনো secret তখনই বা কিছুক্ষণ পর বাতিল হবে এমন বেছে নিলেন।
- অ্যাপের এনভায়রনমেন্টে `STRIPE_WEBHOOK_SECRET` আপডেট করা হয়নি।
- **১০:০১** থেকে প্রতিটা webhook-এ signature যাচাই ব্যর্থ, অ্যাপ `400` দিচ্ছে। Stripe পরে আবার পাঠানোর চেষ্টা করছে।
- গ্রাহকের কার্ড থেকে টাকা কাটছে (PaymentIntent succeeded), কিন্তু অর্ডার "pending", কোর্স আনলক হচ্ছে না।
- **১১:২০** সাপোর্টে ২০টা অভিযোগ। কোনো অ্যালার্ট আসেনি, কারণ webhook failure rate-এর অ্যালার্ট ছিল না।
- **১১:৩৫** QA লগে `order_id` দিয়ে খুঁজে দেখল `webhook signature verification failed`, `http_status: 400`। Stripe-এর webhook ডেলিভারি পেজে ১০:০১ থেকে সব লাল।
- **১১:৫০** নতুন secret দিয়ে কনফিগ আপডেট ও ডিপ্লয়। নতুন ইভেন্ট সফল।
- **১২:১০** আটকে থাকা ইভেন্টগুলো resend করা হলো (Stripe নিজেও retry করছিল)। অর্ডারগুলো paid হলো। QA রিকনসিলিয়েশন চালিয়ে নিশ্চিত হলো কোনো অর্ডার বাদ নেই, কোনোটা দুবার প্রসেস হয়নি ([/lessons/reconciliation-testing/](/lessons/reconciliation-testing/))।

### রিগ্রেশন টেস্ট (staging)

1. ভুল secret সেট করে `stripe trigger payment_intent.succeeded` চালান: অ্যাপ `400` দেয় এবং ১০ মিনিটের মধ্যে অ্যালার্ট আসে।
2. সঠিক secret দিন, ইভেন্ট resend করুন: `200`, অর্ডার paid, একবারই কনফার্মেশন ইমেইল।
3. একই `event_id` আবার পাঠান: অর্ডারে কোনো পরিবর্তন নেই (idempotent)।
4. লগে secret বা পুরো signature হেডার লেখা হয়নি, যাচাই করুন।

Signature যাচাই নিয়ে আরও: [/lessons/webhook-signature-verification/](/lessons/webhook-signature-verification/)।

## হাতেকলমে অনুশীলন

1. Stripe Test Mode-এ একটা পেমেন্ট করুন। Dashboard-এর ডেভেলপার লগে সেই API কলটা খুঁজুন এবং তার Request-Id নোট করুন।
2. Postman-এ Stripe-এর যেকোনো API কল করে রেসপন্সের Headers ট্যাবে `Request-Id` খুঁজুন।
3. নিজের লোকাল অ্যাপ থাকলে webhook হ্যান্ডলারে একটা structured log যোগ করার প্রস্তাব লিখুন: কোন কোন ফিল্ড থাকবে, কোনগুলো কখনো থাকবে না।
4. Stripe CLI দিয়ে লোকালে webhook ফরোয়ার্ড করুন, তারপর অ্যাপে ভুল `whsec_XXXXXXXX` দিয়ে ইভেন্ট ট্রিগার করুন। CLI আউটপুটে `400` দেখুন। ঠিক করে আবার চালান।
5. উপরের ৬টা মেট্রিকের জন্য একটা কাগুজে ড্যাশবোর্ড আঁকুন: কোন গ্রাফ, কোন থ্রেশহোল্ডে অ্যালার্ট।
6. উপরের টেমপ্লেট ব্যবহার করে আপনার দেখা কোনো ছোট বাগের (বা কাল্পনিক ঘটনার) post-mortem লিখুন।

> [!MISTAKE] সাধারণ ভুল
> - লগে শুধু "error" লেখা, কোনো id নেই।
> - ডিবাগের নামে পুরো রিকোয়েস্ট/রেসপন্স বডি লগ করা, যেখানে secret বা কার্ড তথ্য থাকে।
> - অ্যালার্ট বানিয়ে কখনো টেস্ট না করা।
> - শুধু সার্ভারের CPU/মেমরি দেখা, ব্যবসার মেট্রিক (success rate, pending orders) না দেখা।
> - ইনসিডেন্টে Live Mode-এ নিজে থেকে পরীক্ষা চালানো।
> - Post-mortem-এ মানুষকে দোষ দেওয়া, ফলে পরের বার কেউ সত্যি বলে না।
> - ফিক্সের পর রিগ্রেশন টেস্ট না লেখা।

## সারসংক্ষেপ

- Structured log-এ order_id, payment_intent, event_id, Stripe Request-Id থাকলে যেকোনো অর্ডারের গল্প মিনিটে পাওয়া যায়।
- কার্ড ডেটা, key, secret, টোকেন, OTP/PIN কখনো লগে নয়।
- success rate, decline rate, webhook failure rate, p95 latency, pending orders: এগুলোর ড্যাশবোর্ড ও অ্যালার্ট রাখুন, এবং staging-এ অ্যালার্ট টেস্ট করুন।
- ইনসিডেন্টে QA: triage, Test Mode-এ রিপ্রোডিউস, টাইমলাইন, ফিক্স যাচাই।
- Blameless post-mortem সিস্টেমের ফাঁক খোঁজে; শেষে একটা রিগ্রেশন টেস্ট যোগ হয়।
