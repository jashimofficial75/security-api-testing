## সিকিউরিটি টেস্টিং মাইন্ডসেট

### অপব্যবহারকারীর মতো ভাবুন

একজন সাধারণ QA লেখেন: "ইউজার কুপন `EID50` দিলে ৫০% ছাড় পাবে।"

একজন সিকিউরিটি-সচেতন QA সাথে সাথে জিজ্ঞেস করেন:

- একই কুপন দুইবার দিলে কী হয়?
- `eid50` ছোট হাতে দিলে?
- দুইটি কুপন একসাথে?
- কুপন দিয়ে ছাড় পেয়ে অর্ডার বাতিল করলে টাকা কত ফেরত আসে?
- অন্য কারো অ্যাকাউন্টের কুপন ব্যবহার করা যায়?

এটাকে বলে Abuse Case (অপব্যবহারের পরিস্থিতি)। প্রতিটি User Story-র পাশে অন্তত একটি Abuse Case লেখার অভ্যাস করুন।

### Trust Boundary

Trust Boundary (বিশ্বাসের সীমানা) হলো সেই জায়গা যেখানে ডেটা কম-বিশ্বস্ত জায়গা থেকে বেশি-বিশ্বস্ত জায়গায় ঢোকে। একটি সাধারণ পেমেন্ট অ্যাপে:

```text
[ব্রাউজার / মোবাইল অ্যাপ]  --(ইন্টারনেট)-->  [আপনার API সার্ভার]  -->  [ডেটাবেস]
        অবিশ্বস্ত               Boundary ১            বিশ্বস্ত
                                                    |
[Stripe / bKash / SSLCommerz]  --(Webhook)-->  Boundary ২ (সিগনেচার যাচাই লাগবে)
```

প্রতিটি Boundary-তে প্রশ্ন: এখানে যা ঢুকছে, তা কি যাচাই করা হচ্ছে? কে পাঠাচ্ছে তা কি প্রমাণিত?

### ক্লায়েন্ট সবসময় অবিশ্বস্ত

ব্রাউজার বা মোবাইল অ্যাপ ইউজারের হাতে থাকে। তাই:

- লুকানো ফিল্ড, ডিসেবল বাটন, JavaScript ভ্যালিডেশন: সবই বাইপাস করা যায়
- Burp Suite বা OWASP ZAP-এর মতো Proxy (ব্রাউজার আর সার্ভারের মাঝে বসে রিকোয়েস্ট দেখা ও বদলানোর টুল) দিয়ে যেকোনো রিকোয়েস্ট বদলানো যায়
- মোবাইল অ্যাপের কোডও ডিকম্পাইল করে দেখা যায়

নিয়ম: **সিদ্ধান্ত সবসময় সার্ভারে।** দাম, ডিসকাউন্ট, রোল, মালিকানা: সার্ভার নিজে যাচাই করবে, ক্লায়েন্ট যা বলে তা নয়। Proxy দিয়ে রিকোয়েস্ট ধরা হাতেকলমে শিখবেন [Burp ও ZAP লেসনে](/lessons/burp-zap-intercept/)।

> [!TIP] প্রতিটি রিকোয়েস্টে তিনটি প্রশ্ন
> ১. **কে** পাঠাচ্ছে (Authentication)? ২. তার কি **এই কাজের** অনুমতি আছে (Authorization)? ৩. **এই নির্দিষ্ট** রিসোর্সটি কি তার (Ownership)? যেকোনো একটির উত্তর "যাচাই হয় না" হলে সেটা সম্ভাব্য বাগ।

## OWASP কী

OWASP (Open Worldwide Application Security Project) একটি অলাভজনক সংস্থা, যারা ফ্রি গাইড, টুল ও তালিকা প্রকাশ করে। ওয়েবসাইট: [owasp.org](https://owasp.org/)।

OWASP Top 10 হলো ওয়েব অ্যাপ্লিকেশনের সবচেয়ে গুরুত্বপূর্ণ নিরাপত্তা ঝুঁকির একটি সচেতনতামূলক তালিকা। এটা পূর্ণ টেস্ট চেকলিস্ট নয়, বরং "কোথা থেকে শুরু করবেন" তার গাইড। বিস্তারিত টেস্ট পদ্ধতির জন্য OWASP-এর Web Security Testing Guide (WSTG) আর ASVS আছে।

> [!NOTE] কোন সংস্করণ?
> এই লেসনে আমরা ব্যাপকভাবে ব্যবহৃত **২০২১** সংস্করণ ধরে শিখছি। এরপর OWASP Top 10-এর নতুন **২০২৫** সংস্করণ প্রকাশিত হয়েছে, যেখানে কিছু ক্যাটাগরির নাম, ক্রম ও একত্রীকরণ বদলেছে। সর্বশেষ তালিকা সবসময় [OWASP Top 10 প্রজেক্ট পেজে](https://owasp.org/www-project-top-ten/) দেখুন। মূল ধারণাগুলো (অ্যাক্সেস কন্ট্রোল, ইনজেকশন, ভুল কনফিগারেশন) সংস্করণ বদলালেও একই থাকে।

## OWASP Top 10 (2021): পেমেন্টের উদাহরণসহ

| ক্যাটাগরি | সহজ ভাষায় | পেমেন্ট উদাহরণ |
| --- | --- | --- |
| A01 Broken Access Control | ইউজার এমন কিছু করতে পারছে যার অনুমতি নেই | URL-এ `order_id` বদলে অন্যের ইনভয়েস দেখা; কাস্টমার হয়ে রিফান্ড API কল করা |
| A02 Cryptographic Failures | সংবেদনশীল ডেটা ঠিকমতো এনক্রিপ্ট বা সুরক্ষিত নয় | কার্ড নম্বর বা API কি প্লেইন টেক্সটে লগ বা DB-তে; http দিয়ে পেমেন্ট পেজ |
| A03 Injection | ইনপুট কোড বা কোয়েরি হিসেবে চলে যায় (SQL, NoSQL, OS কমান্ড, XSS) | কুপন ফিল্ডে SQL দিয়ে সব কুপন বের হওয়া; অর্ডার নোটে স্ক্রিপ্ট যা অ্যাডমিন প্যানেলে চলে |
| A04 Insecure Design | ডিজাইনেই নিরাপত্তা ভাবা হয়নি | কুপন ব্যবহারের কোনো সীমা নেই; রিফান্ডের পরিমাণ পেমেন্টের চেয়ে বেশি দেওয়া যায় |
| A05 Security Misconfiguration | ভুল সেটিং, ডিফল্ট পাসওয়ার্ড, অপ্রয়োজনীয় ফিচার চালু | প্রোডাকশনে ডিবাগ মোডে স্ট্যাক ট্রেসে কনফিগ দেখানো; খোলা অ্যাডমিন প্যানেল |
| A06 Vulnerable and Outdated Components | পুরনো লাইব্রেরি যাতে জানা দুর্বলতা আছে | বহু বছর পুরনো পেমেন্ট প্লাগইন বা ফ্রেমওয়ার্ক যার CVE প্রকাশিত |
| A07 Identification and Authentication Failures | লগইন ও সেশন দুর্বল | OTP-তে কোনো রেট লিমিট নেই; লগআউটের পরেও টোকেন দিয়ে পেমেন্ট মেথড বদলানো যায় |
| A08 Software and Data Integrity Failures | যাচাই ছাড়া কোড বা ডেটা বিশ্বাস করা | Webhook সিগনেচার যাচাই ছাড়া "পেমেন্ট সফল" মেনে নেওয়া |
| A09 Security Logging and Monitoring Failures | আক্রমণ হলে কেউ টের পায় না | হাজারটা ব্যর্থ কার্ড চেষ্টা (কার্ড টেস্টিং) কোনো অ্যালার্ট দেয় না |
| A10 Server-Side Request Forgery (SSRF) | সার্ভারকে দিয়ে ইচ্ছামতো ঠিকানায় রিকোয়েস্ট পাঠানো | "রিসিপ্ট লোগো URL" ফিচার দিয়ে ইন্টারনাল সার্ভিস বা ক্লাউড মেটাডেটা পড়া |

লক্ষ্য করুন A01 তালিকার শীর্ষে। পেমেন্ট সিস্টেমে সবচেয়ে বেশি ক্ষতিকর বাগগুলোর বড় অংশই অ্যাক্সেস কন্ট্রোল আর বিজনেস লজিক নিয়ে। এগুলো নিয়ে আলাদা লেসন আছে: [পেমেন্ট লজিক দুর্বলতা](/lessons/payment-logic-vulnerabilities/) আর [Auth ও Authorization টেস্টিং](/lessons/auth-authorization-testing/)।

## OWASP API Security Top 10 (2023)

আধুনিক পেমেন্ট সিস্টেম মূলত API দিয়ে চলে: মোবাইল অ্যাপ, ওয়েব ফ্রন্টএন্ড, Webhook, পার্টনার ইন্টিগ্রেশন। API-র নিজস্ব ঝুঁকি আছে বলে OWASP আলাদা তালিকা বানিয়েছে। সর্বশেষ সংস্করণ ২০২৩: [OWASP API Security Project](https://owasp.org/www-project-api-security/)।

| ক্যাটাগরি | সহজ ভাষায় | পেমেন্ট API উদাহরণ |
| --- | --- | --- |
| API1 Broken Object Level Authorization (BOLA) | আইডি বদলে অন্যের অবজেক্ট অ্যাক্সেস | `GET /api/orders/1002` দিয়ে অন্য কাস্টমারের অর্ডার ও ঠিকানা দেখা |
| API2 Broken Authentication | পরিচয় যাচাই দুর্বল | মেয়াদোত্তীর্ণ JWT গ্রহণ করা; পাসওয়ার্ড রিসেট টোকেন অনুমান করা যায় |
| API3 Broken Object Property Level Authorization (BOPLA) | অবজেক্টের নির্দিষ্ট প্রপার্টি দেখা বা বদলানোর অধিকার যাচাই নেই | প্রোফাইল আপডেটে `wallet_balance` বা `role` পাঠালে সেভ হয়ে যায়; রেসপন্সে অন্যের পূর্ণ কার্ড তথ্য |
| API4 Unrestricted Resource Consumption | রিসোর্স ব্যবহারের সীমা নেই | একটি রিকোয়েস্টে `limit=100000` দিয়ে সব ট্রানজ্যাকশন; প্রতিটি OTP-তে খরচের SMS, সীমা ছাড়া |
| API5 Broken Function Level Authorization (BFLA) | ভুল রোল দিয়ে ফাংশন কল করা যায় | কাস্টমার টোকেনে `POST /api/admin/refunds` কাজ করে |
| API6 Unrestricted Access to Sensitive Business Flows | ব্যবসায়িক ফ্লো অটোমেশন দিয়ে অপব্যবহার | বট দিয়ে সব ফ্ল্যাশ সেলের স্টক কিনে নেওয়া; কার্ড টেস্টিংয়ের জন্য চেকআউট ব্যবহার |
| API7 Server Side Request Forgery (SSRF) | ইউজারের দেওয়া URL সার্ভার যাচাই ছাড়া ফেচ করে | "Webhook URL সেট করুন" ফিচারে `http://localhost` দিলে ইন্টারনাল সার্ভিসে রিকোয়েস্ট |
| API8 Security Misconfiguration | ভুল কনফিগ, CORS, হেডার, এরর মেসেজ | যেকোনো অরিজিন থেকে ক্রেডেনশিয়ালসহ CORS অনুমতি; এররে স্ট্যাক ট্রেস |
| API9 Improper Inventory Management | পুরনো বা ভুলে যাওয়া API ভার্সন চালু | `/api/v2` সুরক্ষিত, কিন্তু পুরনো `/api/v1/payments` এখনো চালু এবং যাচাই ছাড়া |
| API10 Unsafe Consumption of APIs | থার্ড-পার্টি API-র ডেটা অন্ধভাবে বিশ্বাস | গেটওয়ের কলব্যাক বা রিডাইরেক্ট প্যারামিটারে `status=success` দেখেই অর্ডার paid, সার্ভার থেকে যাচাই ছাড়া |

### BOLA, BFLA আর BOPLA গুলিয়ে ফেলবেন না

তিনটিই Authorization সমস্যা, কিন্তু আলাদা স্তরে:

| নাম | প্রশ্ন | উদাহরণ |
| --- | --- | --- |
| BOLA (API1) | এই নির্দিষ্ট **অবজেক্ট** কি তোমার? | অর্ডার ১০০২ আমার না, তবু দেখছি |
| BOPLA (API3) | এই অবজেক্টের এই **ফিল্ড** কি তুমি দেখতে বা বদলাতে পারো? | নিজের প্রোফাইল, কিন্তু `role` বদলানো যাচ্ছে |
| BFLA (API5) | এই **ফাংশন** কি তোমার রোলের জন্য? | কাস্টমার হয়ে অ্যাডমিন রিফান্ড API |

> [!NOTE] বাংলাদেশি প্রেক্ষাপটে API10
> SSLCommerz, bKash বা অন্য গেটওয়েতে পেমেন্টের পর ইউজারকে আপনার সাইটে রিডাইরেক্ট করা হয়। সেই রিডাইরেক্ট URL-এর প্যারামিটার ইউজার নিজে বদলাতে পারেন। তাই অর্ডার paid করার আগে সার্ভার থেকে গেটওয়ের ভ্যালিডেশন বা কোয়েরি API দিয়ে যাচাই করতে হয়। বিস্তারিত [বাংলাদেশি গেটওয়ে লেসনে](/lessons/bangladesh-gateways-sandbox/)।

## হাতেকলমে অনুশীলন

1. **Juice Shop চালু করুন** (আগের লেসনে না করে থাকলে):

```bash
docker run --rm -p 3000:3000 bkimminich/juice-shop
```

2. ব্রাউজারে `http://localhost:3000` খুলুন। দুইটি টেস্ট অ্যাকাউন্ট রেজিস্টার করুন, কাল্পনিক ইমেইল দিয়ে, যেমন `tester1@example.test` আর `tester2@example.test`। এটা লোকাল ল্যাব, আসল ইমেইল লাগবে না।
3. ব্রাউজারের DevTools → Network ট্যাব খুলে একটি পণ্য বাস্কেটে যোগ করুন। স্ক্রিনশট বর্ণনা: Network ট্যাবে `/api/BasketItems` বা `/rest/basket/...` ধরনের রিকোয়েস্ট দেখা যাবে, Payload-এ পণ্যের আইডি ও পরিমাণ।
4. প্রতিটি রিকোয়েস্টের জন্য একটি টেবিল বানান: URL, মেথড, কোন আইডি পাঠানো হচ্ছে, কোন Trust Boundary পার হচ্ছে, আর OWASP-এর কোন ক্যাটাগরির ঝুঁকি থাকতে পারে।
5. Juice Shop-এর Score Board খুঁজে বের করুন (এটাও একটা চ্যালেঞ্জ)। সেখানে "Broken Access Control" আর "Improper Input Validation" ক্যাটাগরির চ্যালেঞ্জের নাম পড়ুন, এখনই সমাধান করার দরকার নেই।
6. PortSwigger Academy-তে ফ্রি অ্যাকাউন্ট খুলে "Access control" টপিকের প্রথম Apprentice ল্যাব সমাধান করুন।

```csv
request,method,ids_sent,boundary,possible_owasp_risk
/rest/basket/6,GET,basket id 6,browser->API,API1 BOLA / A01
/api/BasketItems,POST,ProductId + quantity,browser->API,A04 insecure design (negative qty?)
/rest/user/login,POST,email + password,browser->API,A07 / API2
```

> [!MISTAKE] নতুনদের সাধারণ ভুল
> - OWASP Top 10-কে পূর্ণ চেকলিস্ট ভেবে বিজনেস লজিক বাগ মিস করা
> - শুধু UI দিয়ে টেস্ট করা; ডিসেবল বাটন দেখে ভাবা "করা যায় না"
> - BOLA আর BFLA গুলিয়ে ফেলা, ফলে বাগ রিপোর্টে ভুল ক্যাটাগরি
> - ল্যাবের অভ্যাসে আসল সাইটে "একটু" আইডি বদলে দেখা: এটাও অনুমতিহীন অ্যাক্সেস
> - পুরনো সংস্করণের তালিকা মুখস্থ রাখা, নতুন সংস্করণ না দেখা

> [!CHECK] এই লেসন শেষে আপনি পারবেন
> - যেকোনো ফিচারের জন্য অন্তত ৩টি Abuse Case লিখতে
> - একটি অ্যাপের Trust Boundary আঁকতে
> - একটি বাগকে OWASP Top 10 ও API Top 10-এর সঠিক ক্যাটাগরিতে ফেলতে
> - BOLA, BOPLA আর BFLA-র পার্থক্য উদাহরণ দিয়ে বোঝাতে

## সারসংক্ষেপ

- সিকিউরিটি টেস্টিং মানে অপব্যবহারকারীর মতো ভাবা: প্রতিটি User Story-র সাথে Abuse Case
- ক্লায়েন্ট অবিশ্বস্ত; দাম, রোল, মালিকানার সিদ্ধান্ত সবসময় সার্ভারে, প্রতিটি Trust Boundary-তে যাচাই
- OWASP Top 10 (2021) A01 Broken Access Control থেকে A10 SSRF; নতুন ২০২৫ সংস্করণ এসেছে, owasp.org-এ সর্বশেষটি দেখুন
- API Security Top 10 (2023): BOLA, Broken Auth, BOPLA, রিসোর্স, BFLA, বিজনেস ফ্লো, SSRF, কনফিগ, ইনভেন্টরি, থার্ড-পার্টি API
- অনুশীলন শুধু Juice Shop, crAPI, VAmPI, DVWA, PortSwigger Academy আর নিজের Sandbox-এ
